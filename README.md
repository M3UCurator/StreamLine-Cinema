# StreamLine Cinema

A leanback Android TV client for TMDB-powered movie and TV discovery, with a D-pad-first remote UI, instant Playroom playback, library imports, native Media3 playback, addon subtitles, a Live tab for live Stremio addons, user IPTV playlists (M3U/M3U8, XSPF) with XMLTV EPG and a TV guide, and profile-linked Kids Mode where the parent-approved set is a separate library (kids-only titles never appear in adult libraries or discovery) behind PIN lockouts.

Built for older 32-bit TV boxes:

- **ABI:** `armeabi-v7a` only
- **minSdk:** 23 (Android 6.0)
- **targetSdk:** 35, **compileSdk:** 37
- **UI:** Jetpack Compose, custom focus engine tuned for D-pad remotes (no touchscreen required)
- **Player:** Media3 / ExoPlayer 1.11 with HLS, DASH, SmoothStreaming, progressive MP4/MKV, ABR and fast-start load control, embedded and online subtitles, plus an **OPEN WITH** window that hands the stream to a detected player or the system chooser and keeps the app player paused until the transfer completes

Playback is native only: every stream is played by ExoPlayer from a direct media URL. There is no embedded browser and no built-in streaming provider list — titles play from direct links inside imported catalogs or from Stremio addons you register yourself.

## Build

Requirements: JDK 17+ (Android Studio JBR works), Android SDK with platform 37, Gradle 9.6 wrapper included.

```bash
# Windows (Git Bash) or Linux/macOS
./gradlew assembleDebug
# signed release APK (Android debug key, so it installs and updates in place)
./gradlew assembleRelease
# all-ABI release for emulators whose abilist has no armeabi-v7a
./gradlew assembleRelease -PallAbis=true
```

`assembleRelease` also copies its output to the workspace root as `Cinema<ddMMyy>v<iteration>[-allabis].apk`, where `ddMMyy` is the build date and `<iteration>` defaults to `12.88` in `app/build.gradle.kts` (bump it per release with `-PcinemaIteration=12.89`). The iteration also sets `versionName` and derives `versionCode` (`major * 10000 + minor`, so 12.83 → 120083), which is what the in-app updater compares against GitHub release tags.

Output:

```
app/build/outputs/apk/debug/app-debug.apk
app/build/outputs/apk/release/app-release.apk
Cinema<ddMMyy>v<iteration>[-allabis].apk
```

`assembleRelease` signs with `~/.android/debug.keystore` through the `release` `signingConfig`, so the result is a complete v1+v2 signed package instead of an unsigned one the installer rejects. Point `signingConfigs.release` at your own keystore when you distribute it. The default release contains only `lib/armeabi-v7a`; `-PallAbis=true` drops that filter for emulator testing only, so the production APK stays 32-bit. The current pair is `Cinema131126v12.88.apk` (32-bit) and `Cinema131126v12.88-allabis.apk` in the workspace root.

The APK contains only `lib/armeabi-v7a` (plus pure-Java Compose/Media3 code), so it installs on 32-bit Android TV boxes:

```bash
adb connect <tv-box-ip>:5555
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.streamline.cinema/.MainActivity
```

## Releases & updates

Releases are published at **https://github.com/M3UCurator/StreamLine-Cinema/releases**; the newest one is always marked **Latest**. Each release carries two APKs:

- `Cinema<ddMMyy>v<iteration>.apk` — `armeabi-v7a`, for Android TV boxes
- `Cinema<ddMMyy>v<iteration>-allabis.apk` — all ABIs, for emulators and 64-bit devices

To update, download the newer APK from Releases and install it over the existing app (`adb install -r <apk>` or a file manager), or use the in-app updater below. Settings, library, profiles, IPTV sources and watch progress are preserved. All builds are signed with the same Android debug key; a different key cannot install over an existing install, so updates must come from this repository's releases.

### In-app updates (12.77 and later)

The app syncs with this repository's GitHub Releases:

- **At startup** — after a few seconds, when **Settings → About → Check GitHub releases** is on (default), it reads `api.github.com/repos/M3UCurator/StreamLine-Cinema/releases/latest` and compares the tag with the installed iteration as numbers (so v12.100 is newer than v12.99). When a newer release exists, a prompt offers **INSTALL UPDATE**.
- **On demand** — **Settings → About → Updates** shows the current state (`UP TO DATE`, `NO RELEASE`, `OFFLINE`, or the newer tag) with **CHECK NOW**.

**DOWNLOAD & INSTALL** fetches the APK that matches the installed flavor — the `-allabis` asset for an all-ABI install, the 32-bit asset for a TV-box install — into the app cache, then hands it to the system installer through `PackageInstaller`. Android shows its own "update this app" confirmation; the app never installs silently.

The updater needs a release published with **both** APKs attached and marked **Latest**. It reads only the latest non-draft, non-prerelease entry.

> **First update:** builds before 12.77 have no updater. Install 12.77 once by hand (`adb install -r Cinema111126v12.77.apk` or the all-ABI build); every later release can then sync from inside the app.

## First run

1. Open **Settings → Access**.
2. Enter either:
   - a **TMDB v3 API key** (`api_key` query style), or
   - a **TMDB v4 bearer token** (starts with `eyJ`), or
   - an **Express proxy base URL** (see below) if you prefer not to keep the key on the device.
3. Press **TEST CONNECTION**. The result appears inline beside the button (success pill or the HTTP error).
4. The app re-verifies the stored key or proxy on **every startup** (a lightweight `configuration` call) — an invalid key surfaces as `TMDB HTTP 401: Invalid API key…` instead of a silent offline state. Editing or clearing the key in Settings re-runs the check immediately; the top bar no longer carries a status label.
5. Once a key is stored, the field shows `*****` instead of the credential; typing a new value replaces it, and PASTE/clear still work. The key is never echoed back to the screen or a screenshot.
6. Import a catalog from **IMPORT** on the Movies / TV Shows toolbar, or search instantly in **PLAYROOM** from the **SEARCH** button in the top bar.
7. Register a **Stremio addon** in Settings so titles have playable sources, or import a catalog whose `streamUrl` / episode URLs point at direct media files. Subtitle-only addons (such as OpenSubtitles v3) can be registered too, and live addons feed the **Live** tab.

The whole app works in two modes:

| Mode | How TMDB is called |
| --- | --- |
| Direct | App calls `api.themoviedb.org/3` with your key/bearer |
| Proxy | App calls `<proxy>/api/tmdb?path=…` with `X-TMDB-Key` header |

If a proxy is configured, it is used for TMDB details, presets, MDBList parsing and generic JSON imports, with automatic fallback to direct TMDB calls when possible.

## Express proxy server

```
server/
  index.js
  package.json
```

Run it on a PC / NAS / Raspberry Pi reachable from the TV box:

```bash
cd server
npm install
TMDB_API_KEY=your_key_here npm start
# StreamLine Cinema proxy listening on http://0.0.0.0:8787
```

Then set **Settings → Access → Express proxy base URL** to `http://<server-ip>:8787`.

### Endpoints

| Endpoint | Purpose |
| --- | --- |
| `GET /api/health` | Server status, whether a server-side key is configured |
| `GET /api/tmdb?path=movie/popular` | Generic TMDB GET proxy; forwards extra query params |
| `GET /api/tmdb-search?query=dune&type=multi&include_adult=false` | Search proxy returning normalized catalog items |
| `GET /api/tmdb-presets?category=Popular%20Movies` | Discover feed with absolute `w500`/`w1280` image URLs |
| `GET /api/mdblist/parse?url=https://mdblist.com/lists/...` | Server-side HTML scrape of public MDBList pages |
| `GET /api/proxy?url=https://example.com/catalog.json` | Generic JSON/HTML fetch with a browser User-Agent |

TMDB key resolution: `X-TMDB-Key` request header → `?key=` → `TMDB_API_KEY` environment variable.

### `api/p.js` stream proxy

The root-level `api/p.js` is a dependency-free serverless function for hosts such as Vercel (`/api/p`). It is independent of the Express catalog proxy and exists for playback:

| Capability | Behaviour |
| --- | --- |
| CORS | `Access-Control-Allow-Origin: *`, range/preflight headers allowed, length/range headers exposed |
| HTTP on HTTPS | The function fetches the upstream server-side, so an HTTPS deployment can play plain-`http` manifests and segments |
| HLS rewrite | Master/variant playlists, `EXT-X-KEY`, `EXT-X-MAP`, `EXT-X-MEDIA` and segment URIs are rewritten back through `/api/p`, so the whole session carries the same auth |
| Range | Incoming `Range`/`If-Range` are forwarded, and `206`, `Content-Range`, `ETag` and `Last-Modified` pass through |
| Headers | `?h=<base64url JSON>` adds an allowlisted set (UA, Referer, Origin, Cookie, Authorization, Range) to every upstream call |
| Guard | Set `PROXY_TOKEN` to require `?token=…`; rewritten playlist links keep the token |

Example: `https://your-host/api/p?url=https%3A%2F%2Fcdn.example%2Fmaster.m3u8&h=<base64url>`. Deploy the file under `api/` in a Node 18+ project; platform streaming/time limits still apply to long live sessions.

Preset categories are exactly:

- Popular Movies
- Top Rated Movies
- Upcoming Movies
- Now Playing Movies
- Popular TV Shows
- Top Rated TV Shows
- TV Shows Airing Today

MDBList parsing uses the public HTML page (browser User-Agent). The local fallback in `MdbListClient` reads the list's card markup directly with plain regexes (no jsoup, so no `java.util.function`/`java.util.stream` calls on old 4.x boxes): one `<div class="card" …>`, one `<div class="header movie-title" title="Title (Year)">`, one `image.tmdb.org` poster, one `idscore` rating and one `themoviedb.org/(movie|tv)/<id>` link per title. Card markup carries no trustworthy IMDb id — offsets can attach a neighbouring card's `tt…` — so imports store an empty `imdbId` and the addon id is resolved from TMDB when the title is played. Pages without card markup fall back to the older anchor scan. List pages that return a Cloudflare/browser challenge produce a readable error instead of corrupt data.

## Core features

### Global top navigation
A single horizontal tab bar (Home · Movies · TV Shows · Live · Favorites · Settings) keeps the vertical canvas for posters, channels and the hero theater. Left/Right on the remote traverses exactly those six tabs and stops at both ends; Up from the content returns to the bar. **DOWN from the Home tab goes to the hero's PLAY**: Home paints full-bleed under the bar, so Compose's spatial search rejects it as a down candidate (it overlaps the tab rect); the bar therefore carries an explicit down route (`TopTabBar(downFocusRequester = …)` → `homeEntryFocus`) that only Home supplies. **Playroom** and **Import** are hidden routes: they never appear in the bar and open only from the **PLAYROOM** / **IMPORT** buttons on the Movies and TV Shows toolbars, with BACK returning to the tab that launched them. Neither toolbar button renders for Kids profiles — kids take content only from parental approval.

The bar floats over the content as a gradient scrim rather than a solid strip: it is 58 dp tall with a further 34 dp of fade below it, so Home's backdrop runs to the top edge of the screen and dissolves into the bar instead of meeting an opaque band. The left slot is the shared **BrandMark** (gold ▶ tile + `STREAMLINE / CINEMA`); the right slot carries only the active-profile chip.

### Settings layout
Settings is a **two-column page** with a plain rail of every destination and a single-column row list in the pane. The left column (220 dp) carries the **Settings** heading, its one-line description and all eleven sections — **Access, Addons, IPTV & EPG, Parental, Appearance, Discovery, Playback, Network, App Sync, Backup, About** — with no category filters, so every destination is one tap away and the compact rail fits the full list on the 411 dp-tall TV viewport (it still scrolls at large text scales). The right pane keeps the section title, status pills, description and divider fixed while the groups scroll underneath.

Every pane uses the same full-width rows (`SettingsRowFrame`, min 44 dp): title plus a one-line description on the left, the current value and a chevron on the right, with uppercase group headers above each block (`PLAYBACK ENGINE · AUTO`, `STREAM QUALITY · BELOW 4K`). Values that used to be chip grids are now **inline dropdown selectors** (`SettingsSelectRow`): CENTER on a row (or a click) expands its own option list with the current choice checked and moves focus onto that choice, and choosing an option persists it, collapses the list and returns focus to the trigger. The row only closes when focus actually stays outside its group — moving focus into the option list briefly clears the trigger's focus, so the leave handler waits 160 ms and re-checks before collapsing, which keeps remote OK working exactly like a click. This keeps each value on one line at every text scale instead of wrapping a chip grid: engine, quality exclusion, bandwidth cap, buffer tier, decoder type, UA preset, caption size, caption backdrop, DNS preset, library sort, poster orientation/size and the three sync cadences all read as `TITLE / description / VALUE ▾`. Toggles are compact switches, and read-only facts (resolved load-control windows, active DNS servers) are right-aligned info rows. Pane state is still summarised in the header pills (`AUTO · 4K`, `MEDIUM · PORTRAIT`, `DEFAULT PIN · KIDS OFF`), so a section can be understood without opening it. Player behaviour controls now cover everything the engine exposes: caption size and backdrop are persisted in settings and shared with the live player, the one-tap **Weak network** preset (LEAN buffer, 2 Mbps cap, no fast start) sits at the top of **Bandwidth & buffering**, **Clear recent searches** empties the Playroom history, **FORCE STEREO DOWNMIX**, **Next up follows furthest watched**, per-part cache clearing, IPTV **PAUSE/RESUME**, **FORGET DEAD** channel health, the two-step **CLEAR APPROVED** for the Kids library and a dynamic version/ABI line in **About**. The **Source selection** group carries **Auto-play searched streams**, persisted as `autoPlaySearchedStream`: **AUTO** (on) starts the first retrieved source as soon as a movie or episode search finishes, **MANUAL** (off) holds playback, opens the source picker when the search ends and starts the source the viewer picks — closing the picker starts the best source instead. Live channels always tune their single source directly in both modes.

Each IPTV source is a full-width card: name with an **ACTIVE/PAUSED** pill, a meta line (`M3U / M3U8 · 2 channels · no EPG`), the clean location, the parse report and the EPG-shift row, followed by **EDIT**, **RELOAD**, **PAUSE/RESUME** and **REMOVE** on their own row, so long provider names no longer squeeze the metadata.

Navigation is spatial: DOWN from the tab bar enters the pane, LEFT walks back to the rail, UP/DOWN moves between rail rows, pane rows and an open dropdown's options, and CENTER switches the pane or opens/confirms a dropdown. Focused rows take the shared gold focus underline; the selected rail row keeps a gold-tinted fill and its accent bar, so focus and selection stay distinguishable on a remote.

The page **remembers where the viewer was**: the selected section, the rail offset and each section's own pane offset are kept in a process-scoped store (`ScreenStateStore`), so switching to another tab and back — or scrolling deep into one section, leaving and returning — lands on the same section, at the same rail position, with the pane at the same offset. Re-entering also focuses the rail row of that section. Because focusing a control inside a scrollable makes Compose bring it into view, the restored offsets are re-applied for a short window after the focus request so the rail cannot drift. The same rule covers dialogs: cancelling or saving the IPTV **EDIT** dialog returns the focus underline to that source's EDIT button, keeps the rail and the pane exactly where they were, and retries the focus request for ~1 s in case the window has not yet won focus back (the same retry runs after the Import source-removal dialog).

Every other screen keeps its position the same way. Tab content is disposed by `AnimatedContent`, so grids, lists and rails take their `LazyGridState` / `LazyListState` / `ScrollState` from the store instead of `remember…`-ing them locally — Home (hero-adjacent grid, Continue Watching rail, genre chips), Movies/TV Shows, Favorites, Live (catalogs, group chips, channel grid), Playroom (grid, type/recent/A–Z strips), Import (form and sources), Detail (page and season rail) and the Kids curation grids. Returning to a surface also restores focus to the card the viewer left on, and dialogs/modal previews hand focus back to the control that opened them.

### Parental controls
The 18+ filter is no longer a Playroom chip. **Settings → Parental** holds a 4-digit PIN and the **Include adult content (18+)** toggle:

- Setting or changing a PIN requires the current PIN when one already exists; removing the PIN also requires it and forces 18+ back off.
- Turning 18+ **on** opens an inline PIN prompt; the toggle stays off until the correct PIN is entered. Turning it **off** is immediate and never asks for the PIN.
- Without a PIN set, the toggle refuses to turn on and points at the PIN fields.
- Digits are entered with an on-screen keypad (1–9, DEL, CLEAR), because Android TV boxes have no reliable soft keyboard; the four-dot display never shows the digits. Only a salted SHA-256 hash (`parentalPinHash`) is stored in the settings JSON — never the PIN itself — and it rides along with settings backup/restore.
- Upgrades from a build that predates the PIN start with 18+ off: a stored `includeAdult` without a PIN hash is normalized away on load, so adult content can never be reachable without a PIN.
- Removing a custom PIN restores the documented default PIN **1234**, which is also what Kids Mode uses before any custom PIN is set.

### Kids Mode
Kids Mode is not a separate switch: it **is** the active Kids-maturity profile. Selecting a profile whose maturity is **Kids** turns it on, and because `ProfileStore` persists the active profile, the mode survives restarts. `KidsModeManager` (`data/KidsMode.kt`) owns the PIN check, the approved-id set and the mode queries; `CinemaViewModel` exposes the filtered flows and `kidsMode` actions.

- **Approval is ownership.** The parent-approved set *is* the Kids library. `CatalogItem.visibleTo(profile, approved)` gives a Kids profile exactly the approved keys and gives every other profile the rest of the hall, so a title approved for Kids leaves the adult library, favorites, Continue Watching and Home rails at the same moment it appears for the kids; un-approving returns it. The rating filter is bypassed for Kids, so a parent can approve something the age rank would have hidden. Approved keys are `CatalogItem.key` (`movie-<tmdbId>` / `series-<tmdbId>`) and `LiveChannel.key` (`<addonUrl>|<id>`), stored as JSON in `streamline_kids_mode`; the split is derived from that set, so no library migration is needed.
- **Curation.** **Settings → Parental → MANAGE KIDS LIBRARY** opens a full-screen editor titled **Approve what the kids watch** with **Movies & Series** and **Live Channels** tabs. Every card carries `✓ KIDS` or `+ ADD`; CENTER/tap toggles approval immediately. It lists the *unfiltered* library and live channels, so the same screen shows both libraries: approving hides a title from the adult hall and revoking moves it back. The header reads `N approved · these titles and channels live only in Kids profiles`, and closing the editor returns focus to the button that opened it. The Movies & Series tab is split into four kids-genre categories — **Animation**, **Family**, **Adventure** and **Kids** — with no "All" view: the grid always shows one category (Animation on open), matching `CatalogItem.genres` case-insensitively, and the empty-state copy names it. Inside a category the titles are grouped under **MOVIES** and **TV SHOWS** section headers with per-section counts, so movies and series never mix. The editor runs in its own full-screen `Dialog` window, so it owns the focus scope: on a remote, focus enters the first card, arrows move between the tab chips, the cards and **DONE**, DOWN from the tab bar enters the grid, the grid scrolls with focus, and focus cannot wander into the Settings screen behind the dialog. Switching tabs or genre chips keeps focus on the chip the user pressed and resets the shared scroll state to the top.
- **Detail-screen approval.** Every non-Kids detail page carries an **ADD TO KIDS** action that flips to **IN KIDS LIBRARY** once approved; approving a TMDB result imports it first, so the approval always has a visible effect. The button only appears for titles in the hall, and **ADD TO LIBRARY** is hidden for a title that is already approved for Kids, because approval already owns it. It edits the same `streamline_kids_mode` set as the curation editor.
- **Two libraries, one store.** Kids profiles keep only the approved keys; every other profile keeps everything that is *not* approved (still filtered by its maturity rank). Home's hero, Top 10, Because-you-watched, New Releases and genre rails, the local Playroom fallback, the trending mix, `loadRelated` and the remote "because" results all run through `visibleTo`, so an approved kids title can never appear in, or drive, an adult discovery rail. The Live grid, guide and channel-surfing list still drop unapproved channels for Kids.
- **Lockouts.** Every route change funnels through one `openTab` interceptor in `AppRoot`: while a Kids profile is active, **Playroom (search)**, **Import** and **Settings** open the leanback `PinDialog` instead of the screen — including entry points from the Live tab (`ADD ONS`) and Home hero setup. Kids have no acquisition surface of their own: the top-bar **SEARCH** button is not rendered, and the Movies / TV Shows toolbars hide **IMPORT**, so the only way content reaches a Kids profile is parental approval. The PIN gate stays armed behind those routes as a second line of defence. A correct PIN opens that one route for the session; a wrong one shows `That PIN is not correct` and clears the dots.
- **Leaving.** Picking any non-Kids profile from the gate asks for the PIN (`Enter the parental PIN to leave the Kids profile.`), with no bypass when no custom PIN exists — the default 1234 always applies. **MANAGE PROFILES** is disabled (`PROFILES LOCKED`) while a Kids profile is active, so the profile editor cannot be used to delete or weaken the active Kids profile.
- Turning the toggle on in Settings switches to the first Kids profile (creating `Kids` when the household has none) and drops back to Home; turning it off returns to the first non-Kids profile. The parental copy explains that the custom PIN guards Kids Mode and that removing it restores 1234.

### Profiles
The app opens on a **Who's watching?** gate instead of dropping straight into the hall. Profiles are stored in `streamline_profiles`; each one owns its own bucket in the library file (favorites, Continue Watching progress, watched episodes), so switching profiles never mixes two people's history.

- The gate lists one tile per profile (initial + colour), an **Add profile** tile, and the **MANAGE PROFILES** / **CANCEL** footer. The whole gate swallows taps, so nothing behind it can be triggered while it is up. Picking a tile loads that profile; MANAGE turns the tiles into **EDIT** targets that open the editor.
- The editor caps its height to the screen and pins its action row, so **CREATE PROFILE / SAVE / CANCEL / DELETE** stay on screen at 1080p. Fields: name (24 chars), maturity (**Kids / Teen / Adult**), audio language and subtitle language (both applied automatically on the next title and switchable from the player OSD).
- **Maturity** is enforced on every list: `CatalogItem.allowedFor()` filters the hall, resume rails, favorites and recommendations per profile. **Kids** profiles instead see the parent-approved set, which is also removed from every other profile's library and discovery (see *Kids Mode*); the top-bar SEARCH and the Movies / TV Shows IMPORT buttons do not render for Kids, and Settings stays visible but PIN-gated.
- Leaving a Kids profile asks for the parental PIN from *Parental controls* (on-screen keypad, four dots); the default **1234** applies when no custom PIN is set. Leaving any other profile never asks. **MANAGE PROFILES** is locked while Kids Mode is on.
- The active profile appears as a chip in the top bar (`Y You`, `K Kids`) with the live device clock (`HH:mm`) beside it; tapping the chip reopens the gate. Profiles, their names, maturity and language defaults survive restarts and settings backup is unaffected.

### Recommendation rails
Home computes a `HomeFeed` from the active profile's own library and history:

- **Continue Watching** — grouped by title, newest in-progress episode first, white `Resume S2E1` pill and ✕ to clear.
- **Top 10 Today** — ranked cards (1…N) taken from the newest/most-watched titles in the hall; the rank badge is drawn by the rail, not by the poster.
- **Because you watched `<title>`** — seeded by the most recent episode in progress; TMDB `/recommendations` results are matched against titles already in the hall. When TMDB is unreachable (no key/proxy or offline) the rail falls back to same-genre picks from the library instead of showing nothing.
- **New Releases** — the five newest release dates in the profile's library.
- **Genre rows** (`Drama`, `Comedy`, …) — one rail per genre present, capped and de-duplicated against the rows above.

Rails rebuild whenever the library or progress changes (`LaunchedEffect` on both) and never fetch content the user has not added: every resolution goes through the shared catalog, TMDB ids come only from those items, and the API key still travels only to the configured proxy via `X-TMDB-Key`.

### Resume-first playback
- Launching a title with saved progress opens a **resume prompt** first: title, `Resume S2E1 · Signal`, a 3 dp progress bar, `1:03 of 10:34 watched`, and **RESUME** (focused) / **START OVER**. RESUME starts the player at the saved millisecond position (`PlayerActivity.EXTRA_START_MS` → `PlayerScreen.startPositionOverrideMs`, applied once per media); START OVER begins at zero and does not clear the saved row until playback reports new progress.
- **UP NEXT** appears as soon as the credits begin, not only at the last frame: TheIntroDB's credits start (or `preview`, which anime uses for the same end-of-episode boundary) schedules the card minutes before the file ends, so a binge can roll on without sitting through the scroll. The card names the next `SxEy · title` over a draining bar with `Playing in Ns · NEXT ▸ to start now · BACK to cancel`; the countdown is sized to the real credits length and driven by the playhead, so pausing or buffering freezes it instead of racing a wall clock. It auto-plays when the playhead reaches two seconds before the file end, starts immediately on **NEXT**, and **BACK** silences the offer for that episode (the dock then keeps the manual **CREDITS** button). With no credits data the original end-of-file card remains: 8 seconds, cancellable, auto-play at zero.
- Both flows respect the profile language defaults set in the editor, which are applied once per media via `TrackSelectionOverride` (audio) and the subtitle renderer.

### App Sync
Settings → **App Sync** gives each source type its own refresh cadence; the choices are not collective.

| Source type | Default | What a refresh does |
|---|---|---|
| Imported lists | Manual | Re-fetches every saved MDBList / TMDB list / JSON manifest through `syncAllSources()` and merges new titles into the Playroom library. |
| IPTV playlists | Manual | Re-downloads every enabled playlist, re-parses M3U/M3U8/XSPF channels, saves each source's cache and refreshes the XMLTV guide (`refreshEpg`). |
| Stremio addons | App start | Re-fetches every enabled manifest in parallel and re-warms the in-memory manifest cache used by Live and playback. |

- **App start** runs once per process launch (two seconds after the UI settles, in the background). **Manual** never refreshes automatically; use the row's **SYNC NOW**, the existing IPTV **RELOAD** button or Import's own sync controls. **12 hrs / 24 hrs** run when the stored per-type timestamp is older than the interval — checked on launch and every 10 minutes while the app stays open.
- Each type keeps its own timestamp in `streamline_settings` (`sync_last_imports` / `sync_last_iptv` / `sync_last_addons`), so changing one schedule never resets another. The row shows `Last refresh 2 h ago`, `Refreshing now…` or the failure reason; a failed source keeps the titles and playlists it already cached.
- The cadence choices are stored in the settings JSON as `importsSync`, `iptvSync` and `addonsSync`, so they survive backup/restore. Installs upgraded from earlier versions default addons to **App start** (the previous always-sync behavior) and the other two to **Manual**.

### Settings backup
- **EXPORT SETTINGS .JSON** writes `cinema-settings-yyyyMMdd-HHmmss.json` with `{ app, version, exportedAt, settings{} }` to public **Download** through the same MediaStore path as the favorites export. The `settings` object is exactly what `AppSettings.toJson()` persists: TMDB key, proxy URL, adult filter, the parental PIN hash, engine, buffering/ABR, bandwidth cap, buffer tier, sort, poster style, UI sound effects, decoder, stereo downmix, cache-on-exit, UA preset, DNS mode/servers, caption size and backdrop, the next-up preference, the auto-play searched streams flag (`autoPlaySearchedStream`), addons and the three App Sync cadences. The cap and tier persist as `bandwidthCap` (`AUTO`, `MBPS2`, `MBPS5`, `MBPS10`, `MBPS20`) and `bufferTier` (`LEAN`, `BALANCED`, `GENEROUS`); unknown or missing values fall back to `AUTO` and `BALANCED`.
- **IMPORT SETTINGS .JSON** opens the system file picker, accepts either the wrapper above or a bare settings object with known keys, validates it, then replaces the live configuration immediately: `CinemaDns` reconfigures, the Access fields refresh and the TMDB check re-runs against the restored key/proxy.
- The export contains the stored TMDB key, so the card warns to keep the file private. Restoring is a full replace — favorites and the library are not included; use the Favorites tab's own JSON export/import for those.

### Hero Home

Nothing collapses when the artwork is missing: the title, badges and synopsis always render.

They appear only when there is more than one featured title — with a single-item hall the dash row is omitted rather than showing a lone active bar.
- Continue Watching stays the top row below the hero (progress stored per movie / per episode, but the rail groups by title and series so a show appears once at its newest in-progress episode); each card wears a white **Resume** / **Resume S1E3** pill derived from the tracked entry and carries a small **✕** that clears that title's progress and drops it from the rail without touching the library entry or its metadata. Tapping the card opens playback at the saved position.
- **The Hall** below it: a responsive `LazyVerticalGrid` (`GridCells.Adaptive`) of `MediaCard`s projected from `MediaItem` (`data/MediaItem.kt`). Each card fills its grid cell, with poster (or backdrop in landscape), ★ rating badge, resume bar, the white Resume pill when the title is in progress, and genre line. Movie/series type badges are gone — the Movies, TV Shows and Favorites **FILTER** chips already segment the catalog. The Hall has no search field of its own — Playroom owns text search.
- Read-only text fields hand arrow keys back to focus, so DOWN from the hero's action row lands on the genre chips and then the grid instead of being swallowed by the cursor.
- **Hero re-entry restores the full-height layout.** The hero item is taller than the viewport, so focus scrolling a short button inside it parks PLAY against the top edge, clipping the title behind the bar and making UP unreachable. Whenever PLAY gains focus the grid snaps back to item 0 after the focus frame (`gridState.scrollToItem(0)`), so coming up from the rails shows the hero whole and a further UP reaches the Home tab.

### Live tab
Settings-registered addons that declare a `live` / TV-friendly catalog feed the **Live** tab:

- Catalogs are read from `GET {base}/catalog/{type}/{id}.json` for every live addon, listed as focusable chips (`FayaTV · Live and Upcoming`, `FayaTV · Sports`, `FayaTV · Countries Filter`, …). REFRESH re-pulls them and ADD ONS jumps to Settings.
- Catalog `extra` groups from the manifest (FayaTV ships `country-name`, `sub-category` and `category`) render as one horizontal chip row per group above the grid. Picking a value reloads through `GET {base}/catalog/{type}/{id}/{name}={value}.json`, **All** and **Clear all** reset the selection, and switching catalogs always starts from the unfiltered list. `skip` (paging) and `search` (free text) extras never become chips.
- Catalog ids and extra values are percent-encoded as URL path segments, so ids with spaces, parentheses, pipes or non-ASCII characters (`tv_Latino (Spanish)`, `tv_Welcome To Playz Tv | New App`, the two flag-emoji `tv_...Tv` catalogs) resolve instead of collapsing into "no channels". Repeated channel ids inside one catalog are de-duplicated so the grid keeps unique focus keys — FayaTV's 126 catalogs load as `126 live catalogs`.
- The header reports the catalog and channel counts (`126 live catalogs · 24 channels in view`).
- Cards always wear a red **LIVE** badge; scheduled events show their UTC start time and the category line. Promo cards (`category: "Premium"`) are filtered out so the grid only contains playable channels.
- Selecting a card resolves `GET {base}/stream/{type}/{id}.json` and then **probes the link before the player opens**: a non-2xx master, an HLS master whose first variant 403s on an expired `hdntl` token, or a playlist with no variants and no segments (`empty playlist`) is reported inline on the Live screen instead of opening a stalling player. Stream headers returned by the addon are forwarded exactly like movie streams, so token-protected live feeds play.
- **Encrypted feeds:** when the addon only publishes a watch page, the page is scanned for its direct manifest (`resolveWatchPage`) and, for ClearKey feeds, the key pair. The resulting DASH source opens in Media3 with the DRM stack described under *DRM playback*, so FayaTV's `TNT Sports FHD` decrypts and plays instead of stopping at a "premium/DRM feed" message.
- Error text is attached to the channel name: `link expired (HTTP 403)`, `server replied HTTP 451`, `server replied HTTP 404`, `empty playlist`, or `only an external watch page is available (premium/DRM feed)` only when the watch page carries no playable manifest and the addon publishes no direct link. A catalog or manifest failure shows the same banner style, and an empty but valid selection says `{catalog}: this selection returned no channels.`
- Like the movie path, every user-facing failure comes from that specific tapped item; the app never substitutes a placeholder channel.
- **Dead-channel memory and auto-advance:** a channel that fails three times in a row is persisted as dead in `channel_health.json` (`LiveChannel.key`, seven-day decay). Dead channels wear a `DEAD · 3×` badge in the grid, zapping hops over them (Prev/Next and the hidden-OSD LEFT/RIGHT and swipe gestures), and a list whose only neighbours that way are dead stays on the current channel with a transient `Dead channels skipped · no live channel after this one` notice instead of tuning a known-broken entry. A real stream that plays for 20 s READY clears the mark on its own, and the Live header offers **CLEAR DEAD (n)** to forget every mark at once (it deletes the health file).
- **Prefetch while the OSD is open:** opening the OSD prefetches the previous and next channel's manifest (400 ms debounce, cached by the repository), so channel surfing no longer pays full tune latency on every hop. Prefetch is skipped when the OSD is closed so idle playback does not pull extra bandwidth.
- **Parse report:** the header lists `PLAYLIST · <name> · <report>` per source (`4 channels · 1 skipped · 1 malformed`) and `GUIDE · <report>` for the parsed guide, in the warning colour when rows were dropped, so a bad provider row is visible instead of silently shrinking the list. The same report is stored on the source and shown in Settings → IPTV & EPG as `Parsed · …`.
- Verified against the FayaTV manifest `https://fayatv.stravo.site/d/manifest.json`: all 126 catalogs return metas (server sweep), every selection group loaded content on the emulator (Sports → United States → 10 channels, Countries Filter → Animation → 24, General → United States → 24, `Latino (Spanish)` → 23), NBC WGBA and RTP 1 play live in Media3, and channel switching (Previous/Next) tunes neighbouring channels with the same probe. Upstream fallout observed there and handled by the banner: expired FANCODE `hdntl` tokens (403), Plex FAST feeds geo-blocked with 451, dead DAI links (404) and an empty Kinescope master.

### IPTV playlists and EPG
User playlists live under **Settings → IPTV & EPG** and appear as their own catalogs at the top of the Live tab (before addon catalogs, which can number in the hundreds):

- **Sources:** local files (SAF picker or plain path), remote M3U/M3U8, and XSPF playlists. Each row shows the detected kind, cached channel count and whether a guide is linked, with **RELOAD** and **REMOVE** actions plus an **EPG SHIFT** stepper (−1H / −30M / +30M / +1H and AUTO) whenever a guide is linked.
- **Pipe headers:** `https://host/live.m3u8|User-Agent=VLC/3.0&Referer=https://site` injects request headers for that URL, both while downloading the playlist and during playback. Per-channel `http-user-agent` / `http-referrer` `#EXTINF` attributes and `#EXTVLCOPT:http-user-agent=…` lines are merged the same way. The suffix parser never throws and never fails a request: `&` and `|` both separate fields (whitespace allowed, `:` or `=` accepted), values may be single- or double-quoted, `%XX` runs are decoded while a literal `+` is preserved (base64 tokens survive), names are matched case-insensitively so `User-Agent`/`user-agent` collapse to one header, and anything OkHttp would reject — non-token names, non-printable values, `Host`, `Connection`, `Proxy-Connection`, `Upgrade`, `Keep-Alive`, `Content-Length`, `Transfer-Encoding`, `Trailer`, `TE` — is dropped instead of crashing the load. A pipe that yields no valid header stays part of the URL.
- **Extended M3U:** `tvg-id`, `tvg-name`, `tvg-logo`, `group-title`, `tvg-chno`, sticky `#EXTGRP`, relative URLs resolved against the playlist location, and duplicate `tvg-id`s disambiguated (`id#2`) so guide lookups stay unique.
- **Dynamic categories:** every playlist's own `group-title` values (first tag only, so `Sydney;Freeview` becomes `Sydney`) drive the group chips. No category list is hardcoded anywhere in the UI.
- **Schemes:** HTTP(S) HLS (`.m3u8`) and MPEG-DASH (`.mpd`) play natively in Media3, plain `.ts` segments play directly, and a bare stream URL becomes a single channel. `udp://`, `rtp://`, `rtsp://`, `rtmp://` and `mms://` entries are handed to an installed external player (a no-player chooser is expected on a bare emulator); the Live banner names the channel being handed off.
- **Shortened URLs and redirects:** every request walks the redirect chain explicitly (`Http.awaitRedirects`) instead of letting OkHttp hide it, so a short link such as `https://jmp2.uk/stvp-FR200016Y5` resolves to its real manifest host before parsing or playback. The final absolute URL becomes the playlist base for relative entries, the cached single-channel `streamUrl`, and the `PlayOption` handed to Media3 — Media3 resolves HLS variants against the URL it is given, so a short link would otherwise request variants relative to `jmp2.uk`. The walker handles 301/302/303/307/308, relative `Location` values, http→https and https→http switches, stops after 10 hops, rejects loops, and drops `Authorization`/`Cookie` when a hop changes origin or downgrades TLS. Addon probes use the same walker, detect HLS from the final path or `Content-Type` (not the short-link path), resolve the first variant against the final URL, and return the resolved master so playback opens the CDN URL directly. A guide URL that redirects (e.g. `i.mjh.nz → raw.githubusercontent.com`) is followed the same way.
- **Guide discovery:** `url-tvg`, `x-tvg-url` and `tvg-url` are read from the `#EXTM3U` header, and the per-source EPG override field wins when set. XMLTV documents are parsed as a stream (external entities disabled, window from six hours ago to two days ahead, capped at 200,000 programmes / 600 per channel); `.xml.gz` and gzip-mislabeled files are sniffed by magic bytes and decompressed with the platform GZIP decoder.
- **EPG UI:** the Live header reports `EPG <n> ch` once a guide is loaded; cards show the current programme, a progress bar and its time range. **GUIDE** opens a full-screen TV guide with TIME / CHANNEL / NOW / NEXT columns, a progress bar per channel and its own REFRESH EPG / CLOSE actions. Guide lookups match `tvg-id` first and fall back to a normalized channel name (quality tags and punctuation stripped). The screen reads the device clock into a 10 s ticker and passes it to every `nowNext`/progress call, so NOW/NEXT and the bars roll over at programme boundaries without touching the remote.
- **Dates and caching:** XMLTV timestamps (`20261020140000 +0200`, `20261020140000+02:00`, `20261020140000Z`, `2026-10-20T14:00:00Z`, optional milliseconds before the zone, optional space before the zone) are normalized to epoch milliseconds with plain arithmetic (UTC = local − offset) instead of per-programme `Calendar`/`SimpleDateFormat`/regex work; the format coverage is the same as `yyyyMMddHHmmss Z`, `yyyyMMddHHmmss` and `yyyy-MM-dd HH:mm:ss`. A timestamp with no offset is read as UTC, so zoneless guides share one clock and compare directly with `System.currentTimeMillis()`; a provider that publishes local wall clock without a zone is corrected with the per-source **EPG SHIFT** stepper. A 7.8 MB / 14.8 k-programme Sydney guide parses in ~1.3 s on the emulator release build (it took ~65 s with per-call `Calendar` and regex compilation in a debug build). Guides are cached in memory for 15 minutes per URL+headers; the download runs off the UI thread with a 120 s timeout, and a slow or failing guide only adds a failure line under the Live header.
- **Parser hardening:** M3U/XSPF/XMLTV reads go through `CappedInputStream` with a byte ceiling, and documents are scanned for entity-expansion bombs before decoding; playlists cap at 10,000 channels, guides at 24 MB downloaded / 256 MB decoded and 400,000 merged programmes (600 per channel). `IptvStore` writes temp-then-rename with fsync and keeps a `.bak`, and the guide cache holds 4 URLs for 15 minutes, so a hostile or truncated playlist/guide fails cleanly instead of exhausting heap or looping. Adversarial cases (unterminated quotes, nested attributes, repeated entities, truncated XML, a missing `#EXTM3U`, control characters) are covered by `IptvStabilityTest`.
- **Provider time shifts:** some providers stamp the whole guide with a wrong UTC offset and no in-file signal reveals it, so the correction belongs to the source. Detection handles the known case on its own: when every `<channel id>` ends `.za` and every `<programme>` carries the same `+0700` label, the guide is shifted −60 minutes. That signature is exactly `epgshare01`'s `epg_ripper_ZA1.xml.gz`, which publishes a UTC+8 wall clock under a `+0700` label; a mixed guide, a guide without channel ids, or the provider's correction to `+0200` all leave it at 0, so the fix cannot outlive the bug. Each source stores `epgShiftAuto` (default true, written on first save) and `epgShiftMinutes` as a manual override; the steppers switch the source to manual and **AUTO** hands it back to detection. Corrections apply to every programme after parsing the cached guide, before merging — so tap-to-tap it rebuilds NOW/NEXT and the bars from the cached XMLTV without another download, and a guide that is already correct (Sydney `+0000`) is untouched. The settings row reads `EPG SHIFT AUTO -1H`, `EPG SHIFT AUTO` or the manual value, and sources saved before detection existed keep a non-zero shift as manual so nobody's earlier correction is discarded.
- **Visible drift notice:** auto-detection and manual shifts both surface as `◷ <source>: guide is −1h off — adjusted` (formatted as `+2h`, `−1h30m`, …) under the Live header, so a guide that was corrected no longer looks wrong to the viewer. The notice only appears when the applied shift is non-zero.
- **Persisted guide index:** after a successful merge the guide writes a compact channel→programme-offset index to `epg_index.json` (versioned, capped at 60,000 entries). On cold start the ViewModel seeds the Live tab from that index before any network call, so NOW/NEXT and the programme bars render immediately and the full XMLTV parse only refreshes them; a missing, empty or corrupt index is ignored and the next successful parse rewrites it.
- **Streaming parses emit partial results plus a report:** the M3U/XSPF and XMLTV parsers never throw away a whole document for one bad row. Each parse returns the guide/playlist it could build plus a `PlaylistReport(total, skipped, malformed)`: malformed rows (truncated `#EXTINF`, blank or unusable URLs, split `<programme>` tags) are counted, skipped rows (out-of-window programmes, duplicate ids) are counted separately, and the one-line summary (`142 channels · 3 skipped · 1 malformed`) is aggregated across sources and shown in Live and Settings.
- **Pre-flight free space:** `IptvStore` and the guide writer check `StatFs` before writing (payload × 2 for the temp + `.bak` copies, plus 4 MB headroom; skipped when the filesystem reports an unknown `usableSpace`) and fail with an `InsufficientStorageException` message ("Not enough storage to save …") instead of a half-written playlist. **CLEAR CACHE NOW** and the per-part buttons (see *Settings layout*) reclaim channel lists and the guide index first.
- **Device-class caps:** the merged EPG ceiling follows the existing low-RAM profile — 400,000 programmes on 2 GB+ devices, 150,000 on 1 GB hardware (single-source caps 200,000 / 80,000). The guide index caps at 60,000 entries either way so the JSON stays small enough to parse during startup.
- **Corpus and fuzz tests:** `IptvCorpusRecoveryTest` runs single-quoted `tvg-*` attributes with BOM/CRLF, `#EXT-X-DISCONTINUITY`, `#EXT-X-KEY:METHOD=AES-128,URI=…` and `#EXT-X-MEDIA-SEQUENCE` playlists, counts the dropped rows of a real-world-shaped playlist and XMLTV document, round-trips the guide index through a cold start, exercises truncated/zero-byte/corrupt/read-only recovery for `AtomicStore` and `IptvStore`, checks the storage pre-flight boundaries and the device-class caps, and feeds 250 random-byte M3U payloads plus 120 random XMLTV payloads through the parsers. `PlaybackWatchdogTest` covers both watchdog state machines with a fake player (16 tests, including the 20 s live / 35 s on-demand tune deadlines), `NativeStreamProxyTest` covers playlist rewriting, stream ids, upstream-failure tripping and Host-header validation (13 tests), and `HttpTimeoutTest` pins the exact client timeouts (4 tests). All 133 unit tests pass with `./gradlew :app:testDebugUnitTest`.

### Smart search & play
**Settings → Discovery** carries three preferences; every one is optional and off by default.

| Setting | Values | Effect |
| --- | --- | --- |
| Content language | App default (English), English, Hindi, Nepali, Spanish, French, German, Portuguese, Arabic, Japanese, Korean, Russian | TMDB `language` tag (`hi-IN`), the target for ranking, and the label the Playroom header adds as a gold `SMART` pill |
| Preferred country | Any country, US, IN, GB, CA, AU, FR, DE, ES, BR, JP, KR, NP | `with_origin_country` on both discover endpoints plus the market used for release-date bounds, certifications and logo choice |
| Language rule | **Prefer** (default) / **Only** | Prefer stable-partitions results into matches → unknown language → other languages, preserving TMDB order inside each band. Only additionally drops records whose `original_language` is known and different; unknown-language records (library, imported lists, some addons) always stay |

- **Never a silent filter.** `rankByLanguage` moves titles, never removes them, unless the rule is Only; the Playroom header shows the active language and country in gold so the viewer can see why ordering changed. When Only empties the page, the empty state names the language and offers **SHOW ALL**, which re-runs the same query with the rule bypassed.
- **Ranking scope** — the default feed, trending/movie/show rails, genre results, recommendation rails, "more like this" and every text search. Search itself has no TMDB language parameter, so Only is applied client-side after the pages merge.
- **Smart source ordering** — `Settings → Discovery → Source order` (default on) reorders **addon** streams only, and only when at least one source is tagged with the content language or `MULTI`. Tiers are: explicit language tag (0), `MULTI` (1), untagged (2), a different language (3). `VOSTFR`-style tags count as a different language because the audio is original, not French. The catalog's own direct stream always stays first, and quality exclusion is applied after the reorder.
- **Per-profile languages stay separate.** Preferred audio and subtitle tracks remain per profile (`CinemaProfile.audioLanguage` / `subtitleLanguage`); Discovery controls discovery and source ordering, not the player's track selection.
- **Cheap refresh.** Changing a preference force-refreshes Home and genres, drops the genre-list cache (it is language-specific), and re-runs the current Playroom search or the default feed. The proxy forwards `language`, `with_original_language` and `with_origin_country` untouched, so no server change is needed.

### TMDB Playroom
- **One search field for everything.** The Playroom owns text search for the whole app: a single query hits the local library, TMDB and the cached IPTV channel list at once. Local/library matches are merged first, TMDB results follow (350 ms debounce, cancelled requests can never overwrite newer ones), and matching live channels render in a `LiveChannelBand` above the poster grid with their playlist/source label — selecting one tunes it through the same probe path as the Live tab. When only channels match, the band stays visible and the grid shows a *No title matches* state instead of hiding the hits.
- **Deep result set.** `TmdbClient.search()` reads `total_pages` from page 1 and fetches the first five pages concurrently (up to 100 movies/shows), de-duplicating by title key. Later pages are best effort: a failed page leaves the rest of the results intact, and queries with a single page still return after one request.
- **Type-ahead** — the field searches as you type; the **SEARCH** button next to it just re-runs the current query (and is how D-pad users submit without the IME). RECENT chips (persisted as `recentSearches`, cleaned to distinct terms of at least two characters, newest first, capped at 8) re-run a past query and can be cleared in one action.
- **MOOD and genre filters** — mood chips map to genre-id sets and feed the same `with_genres` discover call as the genre chips: movies get *Edge of seat*, *Feel-good*, *Epic* and *True story*, TV gets *Edge of seat*, *Feel-good*, *Binge drama* and *Real world*. Tapping the active mood clears the genre selection. Genre selections are multi-select and pruned when they do not exist in the active type scope.
- **A–Z browse** — when the query is blank and no genre is selected, an A–Z strip browses the Playroom feed by initial via `browseLetter()`; tapping the active letter clears it.
- **Single scroll surface** — the header, RECENT/A–Z strips, banners and the results grid live in one `LazyVerticalGrid` (the header is a full-span item), so the whole page scrolls together; a tall header can no longer squeeze the results into a sliver on short TV viewports.
- **All / Movies / TV Shows pills.** The pills filter the whole page, not just text searches: with TMDB access the default feed calls `movie/popular` for Movies, `tv/popular` for TV Shows and `trending` for All, then merges the library with the same type filter; with TMDB offline the local library is filtered by `CatalogItem.type`. Genre and A–Z browsing already narrow by the active type, and the result count in the header reflects the filtered set. Adult filtering lives in **Settings → Parental** (`include_adult`), not in the Playroom filter row.
- **Retrofit interface** (`data/TmdbApi.kt`) declares the standard TMDB browsing endpoints, one method each, with suspend functions and Gson DTOs:

  ```kotlin
  @GET("genre/movie/list") suspend fun movieGenres(@Query("language") language: String): TmdbGenreList
  @GET("genre/tv/list")    suspend fun tvGenres(@Query("language") language: String): TmdbGenreList
  @GET("discover/movie")   suspend fun discoverMovies(@Query("with_genres") withGenres: String,
                                                      @Query("include_adult") includeAdult: Boolean,
                                                      @Query("sort_by") sortBy: String,
                                                      @Query("primary_release_date.lte") releasedBy: String?,
                                                      @Query("language") language: String,
                                                      @Query("with_original_language") originalLanguage: String?,
                                                      @Query("with_origin_country") originCountry: String?,
                                                      @Query("page") page: Int): TmdbDiscoverPage
  @GET("discover/tv")      suspend fun discoverTv(/* same parameters */): TmdbDiscoverPage
  ```

  The movie and TV genre lists are fetched in parallel on first use, cached for the process, and drive the genre chips. The same interface is served by two Retrofit instances — direct (`api.themoviedb.org`) and proxy (`/api/tmdb?path=…` with `X-TMDB-Key`) — with the proxy tried first.
- **Genre browsing:** genre chips are a multi-select; selected ids are sent comma-separated in `with_genres` (e.g. `28,12`), one discover call per media type, merged and de-duplicated by title key. Each type reads up to five discover pages (TMDB serves 20 titles per page), fetched concurrently after page 1 reports `total_pages`; extra pages are best effort so a single failed page never empties the shelf. MOOD chips use the same pipeline, since a mood is just a preset genre-id set. Switching the type filter prunes ids that do not exist in that scope (a TV-only view drops movie-only ids), so a stale selection cannot produce an empty grid.
- **Sort:** genre results default to **NEWEST** — the current month/year first, then the rest of the catalog in descending release order. The discover call carries `primary_release_date.lte` / `first_air_date.lte` set to the last day of the current month (plus `primary_release_date.desc` / `first_air_date.desc`), and the merged movie+TV list is re-sorted by full release date and then rating. The upper bound is what keeps the page populated: without it TMDB leads with next-year announcements, which the Playroom then drops as future releases. **POPULAR** switches to `popularity.desc` and keeps the returned popularity order. The SORT/NEWEST/POPULAR chips sit in the Playroom header beside the result count.
- **Current-year cutoff:** every Playroom result — search, genre browse, the default feed and the merged local/library titles — passes through `playroomResults()`, which drops anything whose `releaseDate` year is after the device year (`Calendar.getInstance()`). Upcoming TMDB releases never surface; titles without a release date are kept and library entries stay visible.
- Query, type filter and results live in the ViewModel, so switching tabs mid-search restores the exact field state; cancelled requests never overwrite newer results or leave a stale error.
- Full-screen preview modal: backdrop-free poster theater, badges, genres, synopsis.
- **PLAY NOW** streams the movie or a chosen season/episode immediately — no library import.
- **1-CLICK IMPORT** adds the title to the library with artwork and episodic URLs. Imports run in `viewModelScope`, so closing the preview or starting playback cannot cancel them halfway.
- Season chips and lazy episode loading from TMDB.
- Imported and library titles are merged into search results (local matches first) and the default Playroom feed, so imported TMDB lists are visible even without live search. With TMDB access offline, the Playroom falls back to the Cinema Hall instead of going blank.

### Focus continuity and text input
- **`FocusMemory`** (`ui/FocusMemory.kt`) is provided once at the app root through `LocalFocusMemory` and shared by every card surface. Each focused card records its surface and item key; coming back to a screen re-claims that card, so leaving and re-entering a tab no longer resets the cursor to the first poster.
- Recorded surfaces include `home.continue`, `home.top10`, `home.because`, `home.new`, `home.hall`, `home.fav`, the per-genre Home rails, `home.popularMovies` / `home.popularShows`, `movies.grid`, `shows.grid`, `favorites.grid`, `live.grid`, `playroom.grid` and `detail.related`.
- **Back from detail** calls `requestRestore()`, which bumps a tick every card observes; the matching card re-requests focus after the close animation. The detail's originating grid also scrolls its remembered item back into view, and the Playroom keeps its scroll position across the preview modal.
- **Returning from the player re-claims detail focus.** Playback runs in `PlayerActivity`, so the MainActivity window loses focus while it is open and comes back with no focused node — the remote appeared dead on the detail page. `DetailScreen` observes `ON_PAUSE`/`ON_RESUME`; on resume it re-requests the control that started playback (the primary **PLAY/RESUME** button, or the exact episode row, tracked through `onFocusChanged` and a per-episode `FocusRequester`), falling back to PLAY if that row is no longer composed.
- **Home does not steal focus on return** — if the last surface was already on Home, the hero does not force focus back to PLAY, so a viewer who left on the hall keeps their place.
- **Closing the profile gate re-claims the hero** — the gate holds focus while it is open, and removing it leaves nothing focused, so Home bumps a focus signal and requests PLAY. The request is retried once through `View.requestFocusFromTouch()`: a gate picked by touch leaves the window in touch mode with no Android view focus, and without that step Compose's `requestFocus()` returns `false` and the first D-pad press would land on the tab strip instead of PLAY.
- **Text fields are D-pad first, touch friendly.** `TvTextField` only highlights on D-pad focus; CENTER/ENTER enters editing, UP/DOWN leave the field instead of getting stuck in the cursor, and Done hides the keyboard. On touch, the read-only field's own text-input node consumes the tap, so a transparent `matchParentSize` overlay owns the tap while not editing and calls `editing = true` + `requestFocus()` — that is what reliably opens the IME for search, the TMDB key, import URLs and the parental PIN. The overlay is removed once editing so caret placement and selection still work normally.

### Playback
- Direct media URLs (`.mp4`, `.mkv`, `.m3u8`, `.mpd`, `.ism`/`.ismc` and SmoothStreaming `…/Manifest` URLs, …) from catalog entries or Stremio addons play in Media3 ExoPlayer with:
  - HLS, DASH and SmoothStreaming support, adaptive bitrate (can be forced to highest rendition),
  - OkHttp data source carrying the selected player User-Agent, stream headers and the app-wide DNS resolver.
- **Load-control profiles by broadcast type — BALANCED tier, normal RAM (the default):**

  | Broadcast type | min (forward) | max | buffer for playback | after rebuffer |
  | --- | --- | --- | --- | --- |
  | Movies & Series — MP4/MKV (progressive) | 15,000 ms | 50,000 ms | 2,500 ms | 5,000 ms |
  | HLS / DASH — fast start enabled | 3,000 ms | 30,000 ms | 1,200 ms | 2,500 ms |
  | HLS / DASH — fast start disabled | 5,000 ms | 30,000 ms | 2,000 ms | 4,000 ms |

  Progressive files keep a deep 15–50 s forward buffer to absorb jitter; adaptive streams start in 1.2–2 s while still holding up to 30 s. Time is prioritized over byte thresholds for stable high-bitrate playback.
- **Low-RAM profile:** `DeviceProfile.isLowRam` treats a device as low-end when `ActivityManager.isLowRamDevice` is set **or** `memoryClass <= 256`. Those boxes get a fixed buffer window — min **and** max are the same value (8 s HLS/DASH with fast start, 12 s HLS/DASH otherwise, 20 s progressive) with Media3's default 2.5 s playback start and 5 s after-rebuffer constants. The loader therefore holds one small window instead of bursting ahead of the playhead, the byte cap is enforced (`setPrioritizeTimeOverSizeThresholds(false)` with 16 MB for adaptive and 24 MB for progressive sources), and the back buffer drops to 20 s adaptive / 40 s progressive. Video above 1080p is never selected on that profile (`setMaxVideoSize(Int.MAX_VALUE, 1080)`), which keeps a 4K rendition out of a 1 GB decoder's queue even when the stream advertises one.
- **Tiered bandwidth cap and video buffer size:** Settings → **Bandwidth & buffering** exposes two persisted tiers on top of the existing fast-start and ABR toggles, plus the one-tap **Weak network** switch and a **High-capacity buffering** toggle for MP4/MKV; the group hint reads `AUTO`, `N MBPS`, `WEAK NETWORK` or `HIGH CAPACITY` and the pane shows the resolved load-control numbers for the selected tier.
  - **Weak network preset** applies the three settings a bad line actually needs at once: **LEAN** video buffer, **2 MBPS · 480p** cap and **fast start off**. The LEAN tier also drops the native VLC/MPV caches to 0.8 s / 4 s, so one tap moves every engine. Switching it off restores the shipped defaults (BALANCED, `AUTO`, fast start on). Its checked state is derived from those three fields rather than stored separately, so changing the cap or tier by hand turns the switch off instead of leaving it claiming a profile the player is not running. It is covered by `BufferTuningTest`.
  - **Fast-start buffering** is the renamed former "Low latency buffering" toggle: it only shortens the Media3 start and re-buffer deadlines for HLS/DASH (3 s / 1.2 s / 2.5 s versus 5 s / 2 s / 4 s). The app does **not** implement LL-HLS or LL-DASH part loading, so the label and its description now say exactly that instead of implying low-latency streaming.
  - **Bandwidth cap** (`AUTO`, **2 MBPS · 480p**, **5 MBPS · 720p**, **10 MBPS · 1080p**, **20 MBPS · 4K**) sets `setMaxVideoBitrate` on `TrackSelectionParameters` for every source, live and on-demand: ABR may still step down from the ceiling but never picks a rendition above it, and `AUTO` restores the uncapped selector. Each chip pairs the ceiling with the rendition tier it roughly matches, the group hint repeats the active pair, and the cap joins the quality exclusion, the dropped-frame 720p downgrade and the low-RAM 1080p limit in one place, so the lowest effective constraint wins. It is applied to a running player as soon as the setting changes.
  - **Video buffer size** (`LEAN`, `BALANCED`, `GENEROUS`) rebuilds `DefaultLoadControl` from `bufferWindow()` on the next tune:

    | Tier | HLS/DASH forward | Progressive forward | Adaptive start / re-buffer | Progressive start / re-buffer | Back buffer (adaptive / progressive) |
    | --- | --- | --- | --- | --- | --- |
    | LEAN | 2–15 s | 10–30 s | 1 s / 2 s | 2 s / 4 s | 30 s / 60 s |
    | BALANCED | 3–30 s with fast start, 5–30 s otherwise | 15–50 s | 1.2 s / 2.5 s with fast start, 2 s / 4 s otherwise | 2.5 s / 5 s | 60 s / 120 s |
    | GENEROUS | 8–60 s | 20–90 s | 3 s / 6 s | 3 s / 6 s | 90 s / 180 s |

    On the low-RAM profile the tier shrinks the fixed window instead of widening a range: LEAN 5 s, BALANCED 8 s (HLS with fast start) or 12 s, GENEROUS 16 s for adaptive sources, and 10 / 20 / 30 s for progressive ones, with the existing 16 MB / 24 MB byte caps unchanged. BALANCED with fast start reproduces the pre-tier window exactly, so upgraded installs play unchanged; the Settings row prints the resolved `min · max · start · re-buffer` values, and both choices ride along in the settings backup.
  - **Native engine caches** follow the same tier, because libVLC and libmpv keep their own buffers instead of Media3's `DefaultLoadControl`: `nativeCache()` maps LEAN / BALANCED / GENEROUS to mpv `cache-secs` **4 / 10 / 20** and libVLC network+live caching **800 / 1,500 / 4,000 ms** (both are applied at engine construction and logged on `StreamLine:engine`). BALANCED keeps the values both engines shipped with, so the tier only changes anything for installs that move off it. The Playback pane shows the resolved pair in a read-only **VLC / MPV cache** row (`10 s MPV · 1.5 s VLC`), and `BufferTuningTest` asserts the mapping and the BALANCED-is-unchanged guarantee.
  - **High-capacity buffering (MP4 / MKV)** is a separate toggle for progressive files, pinned to **15 s fill · 50 s forward · 2.5 s start · 5 s re-buffer** (`HIGH_CAPACITY_VOD_WINDOW`). It wins over the buffer tier only for non-adaptive playback, on the theory that a film or episode downloaded as one response body can afford the deepest queue the device can hold; turning it on also raises the VLC/MPV caches to 5 s / 30 s, so a switched engine behaves the same. Adaptive HLS/DASH keeps its tier window (segment-based ABR does not benefit from a 50 s progressive buffer); low-RAM devices take the pin too, and their existing byte budget (`setTargetBufferBytes`) still caps how much of that window is actually held, so the toggle cannot exhaust their RAM. Settings prints the resolved numbers in the **MP4 / MKV load control** row, shows `HIGH CAPACITY` in the group hint, the choice rides along in the settings backup (`highCapacityBuffer`), and the player logs `Load control · progressive · 15000/50000 ms · start 2500 ms · re-buffer 5000 ms · back 120000 ms · high capacity` so the active profile can be confirmed from logcat. `BufferTuningTest` covers the pinned window, the adaptive and low-RAM exceptions, and the deepened native caches.
- **Dropped-frame downgrade:** a 15 s monitor samples `PlaybackStats` once the stream has played 10 s. If the drop rate reaches 12 %, the player is capped to 720p for the rest of the session (`Dropped N frames (x %) · capping video at 720p` in `StreamLine:player`). The ceiling joins the same `setMaxVideoSize` constraint as the quality exclusion and the low-RAM cap, so only the lowest of the three wins; single-rendition streams keep playing because Media3 refuses to select nothing.
- **Buffer and reconnect watchdog deadlines:** live tunes get 20 s (`LIVE_TUNE_WATCHDOG_MS`), on-demand tunes 35 s (`VOD_TUNE_WATCHDOG_MS` — a cold TLS + manifest chain still fits, but a CDN that answers and then dribbles nothing surfaces the failure panel instead of an endless spinner), and VLC/mpv tunes 60 s because they discover renditions through the loopback proxy. A live tune that hits its deadline is retried once without the proxy before the panel appears.
- **Transient reconnect (live and on-demand):** a stream that fails with a transient transport code (`ERROR_CODE_IO_NETWORK_CONNECTION_FAILED`, `…_CONNECTION_TIMEOUT`, `…_READ_POSITION_OUT_OF_RANGE` or `…_UNSPECIFIED`) reconnects the same source on its own — three times on live with 5 s, 10 s and 15 s backoff, twice on a film with 3 s and 6 s (`Connection lost · reconnecting in Ns` in both cases) — before the panel and source failover run. A film's retry re-seeks to the snapshotted playhead, so the resume costs nothing. The budget is shared with stall recovery, so a source that keeps failing still escalates. Authorization failures, 4xx/5xx, unsupported and malformed data stay on the error-taxonomy path (malformed data gets one transport retry first), so a dead token is not retried in a loop.
- **Playback sources:** the plan is the item's own direct stream (catalog `streamUrl`) followed by every enabled Stremio addon link. Sources are opened from the dock's **Sources** button or **More → Playback source** in the OSD.
- **Full playable-source search:** the player never declares "No playable sources" until every source has answered. `CinemaRepository.searchPlayableStreams()` emits a `StreamSearchEvent.Step` per source — catalog first, then every enabled addon, queried in parallel on `Dispatchers.IO` with a 20 s cap each — and finishes with `Finished(options, steps)` only after all of them replied. The UI renders that stream live:
  - **Searching (no source yet):** a full-screen “Searching playable sources” overlay lists each source with a spinner, a green ✓ and playable count, a “no playable streams” dash, or a red ✗ with the addon's failure reason (HTTP statuses are trimmed to `HTTP 404 from addon`, timeouts read `no answer within 20 s`). The footer counts the sources searched and only then shows **No playable streams · Searched N sources**.
  - **Searching (catalog stream already playing):** the OSD header shows `Searching playable sources · n/total`, and with the OSD hidden a top-right **SEARCHING SOURCES · n/total** pill tracks the same progress.
  - **Results:** the picker shows a **SEARCH RESULTS** section with the per-source outcome, followed by **PLAYABLE SOURCES** for the sources that answered. Addon links are appended after the catalog source and deduplicated by URL; the picker lists every distinct stream it received and scrolls lazily, so the card count is never capped. When Settings → Playback → **Quality exclusion** hides some of them, the footer states it plainly (`12 of 63 playable sources · 51 skipped by the quality limit in Settings`).
  - Failover is gated on the search: "All N sources failed" appears only after the in-flight search completes, so a slow addon cannot be pre-empted by an error screen.
- **Automatic source failover:** a native playback error triggers the next untried source instead of dead-ending, resuming from the position where the failed stream stopped. Media3 drops a fatal error to `STATE_IDLE`, where `currentPosition` reads 0, so the player mirrors the playhead continuously (`lastKnownPositionMs`) and snapshots it in `onPlayerError` before the old player is released; the VOD failover seeks the new source to that snapshot when it is past 5 s (`Failover → <source> · resume <ms>` in `StreamLine:player`). Live streams never seek on failover because catching up would skip the broadcast. The "Stream interrupted" overlay only appears after every source has been exhausted; RELOAD restarts the round.
- **Playback engine selection:** Settings → Playback → **Playback engine** offers **AUTO** (the built-in Media3 player, used unless another engine is chosen), **BUILT_IN**, **EXTERNAL**, **VLC** and **MPV**. VLC and MPV are in-app engines, not hand-offs: both are wrapped in the same `SimpleBasePlayer` facade as Media3, so the OSD, track selection, subtitles, stats panel, watchdogs and watch progress work unchanged, and the choice is persisted across launches.
  - **VLC (packet-loss recovery)** uses `org.videolan.android:libvlc-all:3.7.7` and is configured for resilience instead of latency: hardware decoding is on (`--avcodec-hw=any`, or `mediacodec` + `--mediacodec-dr` with the **Amlogic fix**), playback keeps the tier's network/live cache (`--network-caching` / `--live-caching` and the per-Media options, 1.5 s at BALANCED) plus a 3 s file cache, and VLC's default late-frame dropping stays enabled — the old `--no-drop-late-frames` / `--no-skip-frames` flags made the frame queue grow until video lagged the audio on weak decoders, and adaptive HLS uses the predictive logic (`--adaptive-logic=predictive`) or `highest` when ABR is off. `--http-reconnect` is deliberately **not** set: with it VLC reopens the source at EOF, so a finite HLS master playlist is re-downloaded forever instead of parsed (the HLS module retries segments itself). The configured User-Agent is installed through `setUserAgent`, and the HTTP-Referer is passed per media.
  - **MPV (direct engine)** uses `dev.jdtech.mpv:libmpv:1.0.0` (minSdk 26, gated at runtime; lower API levels stay on Media3). mpv runs with `hwdec=auto-safe`, `vo=gpu`, a `cache-secs` value taken from the buffer tier (10 s at BALANCED), a 32 MiB forward / 8 MiB back demuxer queue (`demuxer-max-bytes`, `demuxer-max-back-bytes`) and reduced FFmpeg probe limits (`demuxer-lavf-probesize=131072`, `analyzeduration=2` s) so a five-variant master is probed in seconds without growing an unbounded queue on a small heap. The bundled FFmpeg has no Android CA store, so mpv **cannot open TLS origins itself**: every https source is played through the loopback HLS proxy, and `canPlayDirectHttps=false` disables the proxy-bypass retry that would otherwise hand mpv a URL it cannot load.
  - **Native tune window:** libVLC and libmpv discover renditions through the loopback proxy before the first frame, so they get a 60 s live-tune watchdog instead of Media3's 20 s (`NATIVE_TUNE_WATCHDOG_MS` in `ui/player/PlaybackWatchdog.kt`); the failure text names the actual deadline.
- **Quality exclusion:** Settings → Playback → **Quality exclusion** persists a ceiling (`Q4K`, `Q1080`, `Q720`, `Q480`; default off). Every playable source is labelled from its quality tokens (`8k`, `4k`, `2160p`, `1080p`, `720p`, `480p`, …), and selecting e.g. **4K** removes 4K, 2160p and 4320p sources from the player's option set while 1080p, 720p and 480p remain; a source with no detectable quality is never excluded. The filter (`QualityFilter.excludeHighQualitySources`) is covered by unit tests and the chosen ceiling is shown on the chip row.
- **EXTERNAL hand-off:** Settings → Playback → engine **EXTERNAL** hands the current stream straight to the **system chooser** (`Intent.createChooser`), which lists every installed video player that accepts the stream — Just Player, VLC, MPV, MX Player or anything else registered in the box. The target uses `ACTION_VIEW` with `application/x-mpegURL` for HLS, `application/dash+xml` for DASH, `video/x-matroska` for MKV, falling back to a generic video type. `ExternalIntents` attaches the `headers` String[] extra in alternating key/value form (the addon's `proxyHeaders.request` values plus the configured `User-Agent`). When no player is installed the app says so and the built-in engine keeps playing.
- **Header-carrying native playback:** addon streams feed their headers into Media3 through `OkHttpDataSource.Factory.setDefaultRequestProperties`, so CDNs that check Referer/UA answer instead of returning 403. The pipe headers, `behaviorHints.proxyHeaders.request` and the settings UA are merged through one case-insensitive map (`StreamUrls.mergeHeaders`, a `CASE_INSENSITIVE_ORDER` `TreeMap`), so a source can never put both `User-Agent` and `user-agent` on the wire — the duplicate pair is what makes CDNs answer 400 — and the addon's own UA wins over the app default. The native HLS proxy, the source probe and the external `ACTION_VIEW` `headers` extra all go through the same merge.
- **Short links unwrapped before tuning:** an addon URL with no media extension is walked through its 301/302/303/307/308 chain (`Http.awaitRedirects`) while the source list is built — up to four per addon, so a slow redirect cannot stall the search — and the player receives the final absolute manifest URL. That is what makes a shortened link's relative `segment.ts` resolve at the CDN instead of at the shortener, and the credential-stripping rules still apply when a hop changes host.
- **Stream kind decided before the player opens:** `StreamUrls.kindOf` classifies a source from its extension, then the response `Content-Type`, then the first 4 KB of the body (`#EXTM3U`, `<MPD`, `<SmoothStreamingMedia`). The result travels as `PlaybackOption.streamKind` and becomes an explicit `MediaItem.setMimeType(APPLICATION_M3U8 / APPLICATION_MPD / APPLICATION_SS)`, so a token endpoint with no `.m3u8` suffix gets the HLS extractor instead of progressive extraction and `UnrecognizedInputFormatException`. Live channels and bare links that skipped the search get the same resolution at load time; the kind also selects the HLS proxy and the external intent's MIME.
- **Provider session limits on live streams:** a live feed that answers 401, 403 or 429 mid-playback (Flussonic `X-Deny-Reason: cached_negative`, an expired token, a max-sessions ban) is treated as temporary instead of fatal. The player keeps the last decoded frame and shows `Provider is limiting this stream · reconnecting in 20s`; it retries after 20 s, 45 s, 90 s and then every 2 min, always through the same proxied URL so a retry never adds upstream sessions or renews the provider's two-minute negative cache. The escalation only resets after 90 s of continuous playback, and the reconnect path never falls back to the direct URL. Any other playback error still opens the usual RELOAD panel and source failover.
- **Tune watchdog:** a provider that accepts the request and then sends nothing never produces a player error — the retry policy just keeps backing off — so every tune has a hard deadline. Live gets 20 s, on-demand 35 s and the native engines 60 s. If the player is not `READY` by then, the app stops it and retries the direct URL once (proxy bypass); a second miss surfaces `Channel stalled · no video within 20s` for live or `Stream stalled · no video within 35s` for a film, with RELOAD and OPEN WITH instead of an endless spinner. A stream that becomes ready before the deadline clears the watchdog silently.
- **Mid-playback stall watchdog:** a stream that stalls after it has started gets the same treatment as one that never started. Once the player has been `READY` at least once, a 1 s poll compares the playhead and buffered position against anchors and only counts as frozen when neither has moved 250 ms across 15 s of wall time while the player is not paused or scrubbing and no error panel is up. Accumulating movement instead of comparing a per-poll delta means a provider that trickles in a few dozen milliseconds per second keeps playing instead of being misread as dead, and a seek (either direction, even inside a full buffer) re-baselines the anchors instead of counting as progress. A stall first re-prepares the same source after 2 s with `Playback stalled · reconnecting in 2s` (a film re-seeks to the frozen playhead; live re-tunes without one), three times on live and twice on a film on the budget shared with error reconnects; only then does the panel read **Playback stalled** / **Channel stalled** with `Nothing played for 15 seconds.` and hand over to source failover. Each reload re-arms the watchdog on a fresh window. Loader-level timeouts still win when they fire first: a Media3 `ERROR_CODE_TIMEOUT` surfaces the **Connection timed out** panel in a few seconds instead of the old ~70 s wait for `ERROR_CODE_IO_NETWORK_CONNECTION_FAILED`. Both state machines live in `ui/player/PlaybackWatchdog.kt` (`TuneWatchdog`, `StallWatchdog`) behind a six-member `WatchdogPlayer` slice, so `PlaybackWatchdogTest` drives every branch — live and on-demand deadline boundaries, proxy bypass, native/player error, READY-wins, HLS-only bypass, pause/scrub/audio-suppression resets, sub-threshold jitter, slow playhead and buffer trickles, backward seeks with and without a covering buffer, buffer growth after a seek, ENDED and IDLE, plus the recovery budget and backoff caps — with a fake player instead of a device.
- **Retry policy:** transport failures back off 0.5 s, 1 s, 2 s, 4 s and 8 s with up to four media / six other retries. A definitive 4xx (except 408 and 429) fails immediately so failover is not delayed, an unsupported manifest or container fails immediately, and malformed manifest/container data gets exactly one retry (usually a truncated transfer) before it fails instead of grinding through the whole transport budget. `StreamLoadPolicyTest` covers every decision, and `StreamLoadErrorPolicy` feeds it to both the progressive and HLS/DASH/SmoothStreaming factories.
- **Proxy fast-fail:** every proxied stream counts consecutive transport failures (connect/read/socket/timeout). Any HTTP answer, including a 403/429 deny, resets the count because it proves the upstream is reachable. Three failures in a row mark the source unhealthy: the proxy logs `Upstream unreachable after 3 tries · <id>`, tells its listener, and the player drops the proxy and reloads the direct URL once with the `Provider unreachable · reconnecting directly` notice instead of sitting inside Media3's retry budget for over a minute. The counter is consumed on a trip so a fresh attempt starts with a full budget, and the trip is ignored while an error panel is already up.
- **Returning to the proxy after a bypass:** the bypass flag is per-attempt, not permanent. When a direct URL has played continuously for 60 s, the player re-arms proxying; the next RELOAD or tune goes through the loopback proxy again, so playlist rewriting, UA/Referer injection and upstream fail-fast are restored. The running stream is never interrupted: the flag only affects the next prepare (the prepare effect is keyed on player, URL and reload token, deliberately not on the bypass flag).
- **Readable playback errors:** Media3 codes are no longer shown raw. `PlaybackFailure` maps them into **Network**, **Provider**, **Source**, **Format**, **DRM** or **Unknown** with a human title, one-line detail and a suggested action — e.g. `ERROR_CODE_TIMEOUT` → *Connection timed out · The provider stopped sending video. · Check the network connection, then reload.*; HTTP `401/403/407/451` → *Provider denied this stream*; `429` → *Provider is limiting this stream*; `404/410` → *Channel no longer available*; `5xx` → *Provider server error*; parser errors → *Stream data is malformed*; decoder errors → *This stream cannot be decoded · Switch the decoder (HW+ or SW) or choose another source.*; DRM key failures → *Protected stream failed*. Unknown-host, TLS, connect and socket-timeout causes are classified from the cause chain, so offline and CDN failures land under **Network** instead of **Unknown**. Raw codes stay in `StreamLine:player` logcat for diagnosis. The panel still offers RELOAD and OPEN WITH, and the same taxonomy covers the stall and provider-limit panels.
- **Native HLS stream proxy:** HLS playback is served through `NativeStreamProxy`, a loopback HTTP server bound to `127.0.0.1` on a random port with a per-process path token. Media3 opens a local `…/index.m3u8`; the proxy fetches the master playlist, rewrites every variant, key, init-map and segment URI back through itself, forwards `Range`, follows redirects and http↔https switches, and applies the configured UA and stream headers to each upstream call. **Host validation:** every request must carry a loopback Host (`127.0.0.1:<port>` or `localhost:<port>`) matching the bound port; anything else is answered `403 Forbidden` and logged as `Rejected Host …`, so a web page that rebinds its own domain to 127.0.0.1 cannot drive the proxy (DNS rebinding) even before the token check. The per-process token in the path remains the primary guard and is unchanged. Every non-2xx upstream response is logged as `Upstream <code> <X-Deny-Reason> <path>`, which names provider token/session refusals before Media3 reports them. If the server cannot start or the proxied source errors, the player falls back to the original URL once. DASH and progressive files keep the direct path; only HLS is proxied.
- **Manifest fetching under memory pressure:** the loopback proxy rewrites playlists line-by-line straight from the upstream stream into one output buffer (`rewritePlaylistStreaming`, 2 MB input / 6 MB output caps) instead of buffering the body and copying it twice, so a 3 MB master no longer peaks at three times its size before Media3 sees a byte. The shared OkHttp client now runs a bounded `Dispatcher` (24 requests total, 8 per host — the platform default of 64 let a burst of addon probes pile up), and text bodies read through `bodyStringCapped` with per-call ceilings (8 MB catalog/list JSON, 512 KB Stremio probe page, 256 KB TMDB reply). Artwork is loaded by Coil through the same OkHttp client (custom DNS, UA and connection pool) with its memory cache capped at 8 % of the heap. A healthy tune on a channel with no recorded failures no longer rewrites `channel_health.json`; only clearing an existing failure persists.
- **DRM playback:** a `PlaybackOption` can carry a `DrmConfig` (Widevine, PlayReady or ClearKey) and `DrmPlayback.drmSessionManager` turns it into a Media3 `DefaultDrmSessionManager` on `FrameworkMediaDrm`, gated by `FrameworkMediaDrm.isCryptoSchemeSupported`. ClearKey feeds use `LocalMediaDrmCallback` with the key pair lifted from the watch page, and `ClearKeySchemeDataInjector` rewrites the DASH Common PSSH (`urn:mpeg:dash:mp4protection:2011`, default KID) into a ClearKey PSSH via `PsshAtomUtil`. Widevine/PlayReady use `HttpMediaDrmCallback(licenseUrl, …)` with the resolved header set as key-request properties. The config survives the Live → player hand-off as JSON in the `streamline.drm` intent extra, so the player keeps the scheme instead of opening an undecryptable black feed; the `StreamLine:drm` log line reports scheme, license target and header *names* only.
- **FFmpeg audio decoder & stereo downmix:** the build bundles NextLib's prebuilt FFmpeg extension (`io.github.anilbeesetti:nextlib-media3ext`, all ABIs) and appends `FfmpegAudioRenderer` behind the platform decoder, so AC3/EAC3/DTS/TrueHD and other tracks the TV chip cannot decode still play. The dock's **2.0** button cycles forced stereo downmixing: 3–8 channel tracks are folded to 2.0 by Media3's `ChannelMixingAudioProcessor` (5.1/quad via `createForConstantPower`, 6.1/7.1 via explicit matrices), mono/stereo pass through untouched, encoded passthrough is withdrawn so AC3/DTS decode to multichannel PCM first, and the player rebuilds and resumes at the current position. The choice is persisted in settings.
- **OOM / RAM-leak prevention:** the load control evicts media behind the playhead once it is older than the back buffer (60 s adaptive incl. live, 120 s progressive; 20 s / 40 s on the low-RAM profile), so long sessions never accumulate stale segments in memory. The player is released on dispose, its listener and lifecycle observer are unregistered, `PlayerView` is detached, and all long-running effects are composition-scoped so disposal cancels them. When the activity leaves the screen the player pauses (PiP keeps playing — it only triggers `ON_PAUSE`), and live streams get `stop()` instead, which drops the entire buffered back-buffer; on return they re-prepare at the live edge. A live stream left paused for 60 s also flushes its buffer and holds at the live edge instead of growing it.
- **Storage:** the app requests no storage permissions. Library state, settings and progress live in the app-scoped `filesDir` (atomic writes, debounced), and the subtitle loader uses the Storage Access Framework (`ACTION_OPEN_DOCUMENT` plus a persistable read grant), so local `.srt`/`.vtt` files work on scoped-storage devices without `READ_EXTERNAL_STORAGE` / `MANAGE_EXTERNAL_STORAGE`.
- Watch progress is written every 30 s, on a genuine pause and once more when the player is disposed, and feeds Continue Watching / resume. The old 4 s cadence rewrote the whole library JSON 15 times a minute for no benefit.
- **No 2-minute cutoff:** no media client uses a call timeout — a call timeout covers the whole response body, so a 35 s bound aborted playback mid-film. Media reads are instead bounded per socket read: progressive films use a 45 s read timeout with a 30 s write timeout and a 20 s connect timeout, adaptive HLS/DASH playlist and segment reads tighten the read timeout to 30 s, and IPTV/XMLTV document downloads use a 30 s read timeout with no call timeout. The metadata/API client keeps its shorter guards (15 s connect, 25 s read, 35 s call). A read timeout only fires when the peer stops sending bytes; the previous 20 s adaptive read timeout, combined with the 4–6 load retries, exhausted playback right around the two-minute mark as `ERROR_CODE_IO_UNSPECIFIED` / `HttpDataSourceException`, which is why it is 30 s now. The exact values are locked by `app/src/test/java/com/streamline/cinema/data/HttpTimeoutTest.kt`. The configured User-Agent and stream headers are attached both as factory defaults and as per-request properties.
- **Forced TLS 1.2 on Android 4.4:** removed. Pinning the media client's `SSLSocket` to `TLSv1.2` broke stream handshakes on modern CDNs (Media3 surfaced `ERROR_CODE_IO_UNSPECIFIED` / `HttpDataSourceException`), so media reads use the default platform TLS stack again. The long-read guarantees above (no call timeout, bounded socket reads, explicit User-Agent and headers) remain in force.
- **Wake & Wi-Fi locks:** while playback is running **or buffering** the player holds a `PARTIAL_WAKE_LOCK` and a `WIFI_MODE_FULL_LOW_LATENCY` Wi-Fi lock (`WIFI_MODE_FULL_HIGH_PERF` below API 29), and releases both as soon as playback pauses or the player is disposed. Holding them through a rebuffer matters on TV boxes that drop Wi-Fi in doze: the lock used to be released the moment `isPlaying` went false, exactly when the loader needed the radio most.
- **Pipe-syntax headers:** any stream URL can carry its own headers with `https://cdn/stream.m3u8|User-Agent=…&Referer=…`, for live channels, films, episodes and addon sources alike. `StreamUrls.parse` splits on the first `|` that is followed by a valid `Name=value` (so `|` inside a token is left alone), accepts `&` or `|` between fields, honours quoted values, decodes `%XX` without turning `+` into a space, and sanitises the result: invalid header names, control characters and HTTP framing headers (`Host`, `Connection`, `Keep-Alive`, `Content-Length`, …) are discarded rather than handed to OkHttp, where a single bad name would fail the request. `mergeHeaders` then unions the result with the headers the addon/catalog supplied in one `CASE_INSENSITIVE_ORDER` map (explicit option headers win), and the app applies it to Media3, the native HLS proxy, the source probe, external hand-off and the player hand-off intent — handy for short-lived tokens and hotlink-protected manifests. `StreamUrls.withHeaders` rebuilds the same syntax (values `%20`-encoded, `+` left literal) for persisted sources, so a parsed URL round-trips. Junk suffixes degrade to "no headers" instead of a failed playback, and the cases are covered by `StreamSourceTest`.
- Settings includes **PREVIEW HLS** and **PREVIEW DASH** sample streams to validate the native engine.

### Hardware & display
Settings → Playback → **Hardware & display** carries three device-level switches. The group hint reads `FIX · AFR`, `AMLOGIC FIX`, `AFR` or `STOCK` so the pane says at a glance what the player will do.

- **Amlogic fix (tunneling)** forces the MediaCodec direct path instead of letting each engine pick a generic hardware path. The built-in engine calls `DefaultRenderersFactory.forceEnableMediaCodecAsynchronousQueueing()` and `DefaultTrackSelector.setTunnelingEnabled(true)`; VLC switches `--avcodec-hw` from `any` to `mediacodec` and adds `--mediacodec-dr`; MPV switches `hwdec` from `auto-safe` to `mediacodec`. It is meant for Amlogic boxes whose vendor frame parser rejects streams that are not strictly MediaCodec-conformant; on a plain emulator (no vendor decoder) the forced path can leave video undecoded, which is why it is off by default. The resolved engine options are logged at construction (`StreamLine:engine`: `vlc caching=1500ms amlogic=true hw=mediacodec+mediacodec-dr`, `mpv cache-secs=10 amlogic=true hwdec=mediacodec`).
- **Auto frame rate matching (AFR)** sets `WindowManager.LayoutParams.preferredDisplayModeId` on the player window to the display mode whose refresh rate matches the source (23.976, 24, 50 or 60 Hz) and restores the original mode when the player is disposed. Only modes at the current resolution are considered, and a rate more than 0.75 Hz away keeps the panel as it is, so a single-mode or 50 Hz panel is never forced to 60 Hz. The rate comes from ExoPlayer's selected video format or from the video `Tracks` entry that VLC and MPV publish (`frameRateNum/frameRateDen`, mpv `container-fps`); a native engine that publishes its track after the first decoded frame triggers a re-check, and `StreamLine:afr` logs each decision (`60.00 Hz source · 60.00 Hz display kept (1 modes)` on the emulator's single-mode panel, `… source → … mode N` when a mode is applied and `Restored display mode N` on exit).
- **Unrestricted battery usage** checks `PowerManager.isIgnoringBatteryOptimizations` and sends `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` when enabled, so Doze and the background app limits cannot kill the player's sockets or drop its buffers. The row re-reads the state on every return to the screen; disabling it opens the system battery-optimisation list instead of silently revoking the exemption, and a device without that panel says so and leaves the playback wake locks as the fallback.

### Stremio addons
Settings → **Addons** registers community addons that speak the [Stremio addon protocol](https://github.com/Stremio/stremio-addon-sdk):

- **Addon sync on startup:** two seconds after launch the app re-fetches every enabled addon's manifest in the background and warms an in-memory manifest cache. The Live tab and playback queries then use fresh catalogs without a first-tap stall; offline addons silently keep their previous cache entry. This is the addon row's **App start** cadence in Settings → App Sync and can be changed to Manual / 12 hrs / 24 hrs independently of imports and IPTV.
- **RAM-safe addon parsing:** addon replies are read with hard byte caps — 2 MiB per manifest, 4 MiB per stream/subtitle/catalog reply, 4 KiB for error bodies — and item caps (64 catalogs per manifest, 64 streams, 100 subtitle tracks, 500 channels per catalog). An oversized or broken addon fails with a readable error instead of exhausting the heap on a 32-bit TV box.
- The manifest (`GET {base}/manifest.json`) is fetched and validated on save: it must declare either a `stream` or a `subtitles` resource, so subtitle-only addons can be registered next to stream addons. Name, version, resources, types and idPrefixes are read from the manifest; the manifest name labels every stream.
- Playback queries `GET {base}/stream/{type}/{id}.json` in parallel for every enabled addon, with `type` = `movie`/`series`. The id is tried as the stored **IMDb `tt…` id first** (`tt1877830`, or `tt0944947:2:5` for an episode) and then as `tmdb:550` / `tmdb:1399:2:5`; the first id that answers with at least one stream wins. Characters with `idPrefixes: ["tt"]` (OpenSubtitles, many stream addons) only reply to the IMDb form.
- **Identity, not proximity.** Only the item's own TMDB id is authoritative (`tmdb:<id>`, or `tmdb:<id>:<season>:<episode>`). The `tt…` id is queried only after TMDB confirmed it for that title — either the item came from a TMDB fetch or the id is resolved on demand through the title's `external_ids` — so a malformed or borrowed `tt…` id is never sent. Imports no longer scrape IMDb ids from list-card offsets. An item without a TMDB id is never searched. A series with no season/episode has no query ids at all instead of silently becoming S1E1; the player shows "no episode selected" and the detail page offers the episode list. Addon replies are then filtered by their own labels: a stream naming another `SxxEyy` / `Season N Episode M` / `NxM` (or an `S01E01-E02` range that does not include the requested episode) is rejected, a `Season N` pack is accepted only for that season, an episode token that cannot be parsed (`Episode 7` with no season) is rejected rather than waved through as unlabelled, `16x9`-style aspect ratios are not read as episodes, and only genuinely unlabelled streams pass. Rejections surface in the search row (`no playable streams · 4 wrong episode`), and only surviving streams can be picked, so "Next episode" always searches the episode the OSD names.
- Subtitles come from the same addons via `GET {base}/subtitles/{type}/{id}.json`, also IMDb-first with a `tmdb:` fallback using the same identity rules, deduplicated by URL, sorted English-first and capped at 60 tracks.
- Each returned `StreamItem` with a direct `url` becomes a player option (HLS/DASH/progressive all open in Media3). `behaviorHints.proxyHeaders.request` is copied into the option headers (values may be plain strings or `{ "value": "…" }`), which Media3 and external players then send.
- Streams that only expose an `externalUrl` page are skipped, because the client has no embedded browser.
- Picker labels use the stream `name`; addons that leave it empty (Hyper does) fall back to the stream `title`, so qualities stay distinguishable.
- Addon lookups run inside the full playable-source search (20 s per addon, parallel): the catalog stream starts playback immediately when present, and addon links are appended after it, deduplicated and capped at 16 per title. The player shows the search iteration until every addon answers.
- Addons can be paused/resumed (ACTIVE/PAUSED chip), removed, reordered with the **▲ / ▼** buttons on every row (the order is persisted and drives source listing, ▲ is disabled on the first row and ▼ on the last), and up to 8 can be stored in `streamline_settings`.

Verified against `https://hyper.stravo.site/local/manifest.json` (Hyper 0.18.5, `idPrefixes` `tt`, `tmdb:`, `tvdb:`). For `tmdb:550` it returns four direct HLS-less sources: one HEVC DASH manifest that needs both `Referer` and `X-MB-Token` (403 without them) and three H.264 MP4 renditions that need `Referer` (429 without it) — every header is carried by the option and applied to all ExoPlayer requests, including DASH segments. `tmdb:94605:1:1` resolves the same way for series. Its upsell entries (`Go Premium`, `Change Audio Dub`) arrive as `externalUrl` and are skipped. Episode ids the addon does not index answer `404`, which the repository treats as "no sources from that addon".

Verified against `https://opensubtitles-v3.strem.io/manifest.json` (OpenSubtitles v3, `resources: ["subtitles"]`, `idPrefixes: ["tt"]`). For The Batman it answers `tmdb:414906` with `{"subtitles":[]}` but `tt1877830` with a full English list, which is why the IMDb id is tried first. With it registered, the player's SUBTITLES panel shows **LOAD 60 ONLINE SUBTITLES**; enabling them reloads the stream with the first English track marked as default and subtitles render over the video.

`app/src/test/.../StremioAddonTest.kt` exercises the real clients: `./gradlew testDebugUnitTest` (the live checks skip themselves when the host is unreachable). `contentIdsPreferImdbForAddonLookups` pins the id ordering, `StreamIdentityTest` pins the identity rules (verified IMDb ids, no series query without an episode, malformed ids rejected, episode/season label matching), and `MdbListParseTest` pins the card-based MDBList parser against captured markup.

### Decoder type
Settings → Playback selects how Media3 builds its `DefaultRenderersFactory`:

| Mode | Selector | Decoder fallback |
| --- | --- | --- |
| **AUTO** (default) | Media3 default | enabled |
| **HW** | Media3 default | disabled — strict hardware decode |
| **HW+** | custom selector sorting `MediaCodecInfo.hardwareAccelerated` first | enabled — aggressive hardware-first with automatic software fallback |
| **SW** | `MediaCodecSelector.PREFER_SOFTWARE` | enabled |

The same cycle is available from the player OSD (tap the decoder chip) and takes effect on the next preparation.

### DNS resolver
Settings → **Network** configures the resolver used by every OkHttp call (TMDB, MDBList and the player's data source). Android has no API to change system DNS without a VPN service, so the app routes name lookups through its own `Dns` implementation instead:

- **Presets:** System (default), Cloudflare, Google, Quad9, AdGuard — presets use DNS-over-HTTPS (`https://…/dns-query`, wire-format POST).
- **Custom:** add up to 6 servers — plain IPv4/IPv6 (`1.1.1.1`, `[2606:4700:4700::1111]`), `ip:port`, or an `https://` DoH endpoint. Custom entries switch the mode to Custom automatically; each can be removed.
- **Resolution order:** every configured server is raced in parallel on a small daemon pool (`MultiDns`), so a dead resolver costs one timeout instead of blocking the next; the first non-empty answer wins and the system resolver remains the last-resort fallback. Per-query budgets are deliberately short — UDP :53 is a single 3 s attempt per record type (the old 2 × 4 s × 2-record loop could stall a tune for 16 s) and DoH uses 4 s connect / 4 s read / 5 s call. Results are cached in memory for 120 s.
- **TEST DNS** resolves `www.google.com` through the current configuration and reports latency or the failure reason.
- Changes apply immediately and persist in `streamline_settings`; the Http client picks them up through a stable router object, so no client rebuild is needed.

Strict CDN edge filters often reject unknown clients. Settings → Playback selects a User-Agent preset that is attached to the native player's data source:

| TiviMate 5.0.4 | `TiviMate/5.0.4 (Linux; Android 12) Android TV` |

The full UA string is shown under the chips so you can confirm exactly what leaves the device. External hand-off attaches the selected UA to the `headers` extra (Just Player and VLC use it) and only falls back to the player's own UA when the extra is ignored.

### Player OSD
The overlay sits above the hardware-accelerated video surface, driven entirely by remote input, in a single global layout:

- **Lifecycle:** any key press while hidden wakes the OSD (focus lands on PLAY/PAUSE); a tap or swipe on the video wakes it too. A touch-woken OSD cannot take programmatic focus (Android touch mode), so the first remote key lands on PLAY/PAUSE and OK hands focus straight to the transport row. The OSD fades out after 4 s of inactivity, and the hide path clears every focus zone so the next wake always starts clean.
- **D-pad zones (remote first):** three explicit zones — header (← back), timeline (seek bar on-demand, programme timeline for live) and dock (transport row). UP moves dock → timeline → back button; DOWN moves back → dock, timeline → dock and dock → hide, so a remote can never get trapped. LEFT/RIGHT walk the dock in reading order with no diagonal leaps, and scrub ±10 s while the seek bar is focused. OK activates, BACK closes a panel, then the OSD, then the player. Focus observers sit above their `focusable` node, so highlights and hints track the real focus state.
- **Non-destructive seeking:** the seek bar and the `−10s` / `+10s` buttons move the playhead without tearing down the stream. Dragging pauses only the playhead — the surface stays attached and keeps rendering the frame at the touched position — and preview seeks are throttled to one every 250 ms; releasing applies the exact position and resumes if playback was running. The player is built with `setKeepContentOnPlayerReset(true)`, so no seek ever flashes a black surface or an error panel, and `lastKnownPositionMs` is updated on every seek so a failure at the new position still resumes there.
- **Buffer indicator:** the seek track carries three layers — the dim rail, a solid grey band for the span the player has already loaded, and the gold playhead on top. The band is read from `Player.bufferedPosition` on the same 1 s tick as the playhead and clamped so it never sits behind the gold, so it shows how much headroom a slow source has before the next stall. Engines that only publish a playhead (VLC and MPV report buffered = position) simply draw no band. Live keeps its guide-based programme bar, where a player buffer has no meaning.
- **Skip recap, intro & credits:** boundaries come from [TheIntroDB](https://theintrodb.org) (`/v3/media?tmdb_id=…&season=…&episode=…`), looked up per episode from its TMDB id, so anime works the same as live-action — MAL/AniDB ids are not accepted by the API and are never sent, and `duration_ms` is never sent either because it makes the service drop `credits`. While the playhead sits inside a segment a gold floating pill (**RECAP**, **INTRO** or **CREDITS**) appears at the far right of the timeline, clear above the seek bar; OK on it jumps to that segment's end and hands focus back to the transport row. A missing `start_ms` means the segment begins at 0, a null `end_ms` means it runs to the end of the file, and anime's `preview` entry stands in for a missing `credits` one. Junk entries are discarded rather than offered — zero-length pairs, reversed ranges, a credits block that starts at 0 or leaves less than 30 s of tail, and segments past the file's real duration. Ten-second lead-in, a 2 s tail guard and a 3 s minimum gain keep a button from appearing for a skip that saves nothing.
- **Cold opens stay untouched:** once an episode has an answer from the database, no intro segment means the episode genuinely has none, so the old duration heuristic stays silent. The heuristic (`90 s` for a 12-minute-plus file, `75 s` above 6 minutes, offered from 12 s) only appears while the lookup is still pending or the service is unreachable, and a 4 s timeout keeps the first few seconds of playback waiting on data at most that long. Movies skip the lookup entirely.
- **Responses are cached and rate-limit aware:** answers (including "no segments") live in a 300-entry on-disk cache under `files/introdb/` — 14 days for a hit, 2 days for a miss — backed by a 24-entry LRU, so a rewatch, a resumed episode or the prefetched successor never re-queries. A `429` parks further lookups for the window named by `X-RateLimit-Reset` (clamped to 1–60 s) and serves stale cache meanwhile; an IO error leaves the previous cache entry in place. The next episode's segments are prefetched right after the current episode resolves, so its boundaries are in hand before its credits begin.
- **Live channel switching:** when the player is opened from the Live tab it carries the catalog's channel list. LEFT/RIGHT with the OSD hidden, Previous/Next in the dock (labelled *Previous/Next channel*) and a horizontal swipe all tune the neighbouring channel. Each tune resolves that channel's stream with a spinner, discards stale answers and shows `CH n/total · name` in the trick-play pill.
- **Live OSD timeline:** for a channel the timeline row is the guide's current programme instead of a seek bar — the programme title on its own line, then `HH:mm` start · elapsed gold bar · `HH:mm` end (wall-clock labels in the device timezone), then one `NEXT · <title> · HH:mm` line. The window comes from `EpgGuide.nowNext` on a one-second clock, so the bar advances and rolls over to the next programme on its own; the guide is read through the repository's warmed cache, and a guide miss falls back to the channel name with `NEXT · Guide data unavailable`. The dock's UP target stays on the transport row because there is no seek bar to land on, and the player-buffer segment has been removed from every seek bar: the OSD only ever shows playback position, never buffer fill.
- **Back navigation:** a vector ← button in the top-left corner closes the player (`finish()`), or steps back out of any open panel first.
- **Minimal header:** only human-readable metadata — the show title and episode label (e.g. `Test Rails — S1 E2: Third Rails`), the system clock, and one line underneath with length (or movie/TV runtime) and the source string. No raw file hashes or internal names are ever shown.
- **Unified bottom dock:** one cohesive overlay above a smooth black-to-transparent (deep navy) gradient scrim, holding the timeline (playhead row for on-demand, programme window for live) and a single horizontal control row: `⏮ Previous` (far left) · `−10s` · PLAY/PAUSE (larger, centered) · `+10s` · `Next ⏭` (far right) · Display/Aspect toggle · **Sources** · **quality** (when two or more source resolutions are available, or the live stream carries several adaptive renditions) · Subtitles/CC toggle · Decoder selector showing the active mode as text (`AUTO` / `HW` / `HW+` / `SW`) · stereo downmix (`2.0`, highlighted when on) · overflow ⋮. Labels are 14–16 sp high-contrast with vector glyphs and dynamic tooltips in a gold hint line; a single bright gold focus indicator tracks the D-pad.
- **D-pad ergonomics:** the dock is chained strictly linearly left/right (no diagonal leaps) and Previous/Next disable themselves when there is no previous/next episode or channel. A disabled NEXT never dead-ends the row: RIGHT from `+10s` lands on the Display/Aspect button and LEFT from Display walks back the same way. UP jumps straight to the seek bar (for live, where there is no seek bar, to the transport row; UP again → back button), and a second UP from the seek bar moves onto the floating skip pill while a segment is offered — DOWN from the pill returns to the bar. DOWN dismisses the OSD from the dock, and the timeline scrubs with LEFT/RIGHT (±10 s) or tap/drag. Every control reports its label into the gold hint line when focused.
The lock pill owns focus while controls are locked, including when the OSD is hidden; D-pad keys and BACK are consumed there (`BACK` never reaches the back handler while locked), so a remote can neither dead-end on the root surface nor exit the player mid-film. Hold OK/Enter for 1.4 s, or press and hold the pill on a touchscreen, to unlock.
- **OPEN WITH window:** ⋮ → **Play in external player** (or **OPEN WITH** on a stall/failure panel) pauses the current player and opens a focused picker titled *OPEN WITH ANDROID PLAYER*: the system program chooser is the default row (`ACTION_VIEW` badge), followed by every detected player with its package id and decoder note, a read-only **Raw stream URL** field with **COPY**, and a pinned **DONE (BACK TO PLAYER)** that returns to the paused player at the same position. Only the row list scrolls on short screens, so DONE is always on screen. The app player is never torn down while the picker is open, so no second instance starts; a named-player launch finishes the app player only after that app has actually covered the screen.
- **Overflow (⋮) panel:** nested secondary menus in a focused dialog — **Info** (async fetch of codec details, stream bitrates, decoder mode, ABR state, source, file name, URL and raw file hash), **Playback stats** (the stats-for-nerds panel), **Play in external player**, **Audio track**, **Audio boost/volume**, **EQ**, **Speed** (0.5×/0.75×/1×/1.25×/1.5×/2×, pitch preserved via the Media3 playback-parameter pipeline), **Display**, **Subtitles**, **Sources**, **Stream quality** (when two or more source resolutions are available, or for a live adaptive ladder), PiP (Android 8+), lock, flip and reload.
- **Stats for nerds:** **Playback stats** opens an on-demand panel fed by Media3's `PlaybackStatsListener` and sampled once a second while it is visible (nothing is collected while the panel is closed). Rows: resolution (`1920 × 1080` from the active video format, falling back to the decoded pixel size), frame rate, video codec, **video bitrate** (the active rendition's own bitrate, falling back to the mean once it is known), **bandwidth estimate** (the live reading from the `DefaultBandwidthMeter` shared with ABR, falling back to the mean), dropped frames with drop rate, audio underruns with per-minute rate, rebuffer count with longest stall, buffered duration, audio track, decoder mode, delivery (`Direct` / `Native proxy`), live vs on demand, and the source name. The player owns one meter instance (`PlaybackBandwidth`) and hands it to both `DefaultBandwidthMeter`-backed ABR and the panel, so the estimate on screen is the number the selector is actually using, and pairing it with the selected rendition's bitrate shows how much headroom ABR is leaving. Unknown counters read `—` rather than zero, so a stream that has not reported yet is distinguishable from a clean one.
- **Aspect ratio:** the dock toggle and the PICTURE panel cycle **Original** (surface sized to the stream's coded pixel size) → **Fit** (whole frame letterboxed) → **16:9** and **18:9** (the picture is constrained to a forced frame of that ratio and filled) → **Stretch** (distorted to the screen) → **Crop** (zoomed to fill, edges trimmed). The default is Fit; **Reset aspect** returns to it. Streams are never re-encoded — only the surface geometry changes.
- **Sources & quality:** the dock's Sources button opens the same per-source picker as **More → Playback source** (search iteration plus every playable link). The quality button appears as soon as the playable set carries two or more distinct resolutions; it lists them highest-first (8K/4K/2160p/1440p/1080p/720p/…) and switches to the first source carrying the chosen resolution, resuming at the current position.
- **Live quality limit:** a live HLS/DASH stream whose manifest exposes multiple video renditions (they arrive as video tracks in one adaptive group) also shows the quality button even when there is only one URL. Its panel lists **AUTO** plus every supported rendition height, best first, and applies `TrackSelectionParameters.setMaxVideoSize(width = MAX, height = cap)` so the selector can never pick a taller rendition; ABR may still step below the cap when bandwidth drops, and **AUTO** clears the constraint (`clearVideoSizeConstraints()`) so the full ladder is available again. The dock button and the overflow value show the active cap (e.g. `720p`) or `AUTO`. For fixed multi-source sets the same panel keeps the **Source quality** rows.
- **Subtitle panel:** embedded text tracks (with language / WebVTT labels), **Off**, **LOAD .SRT / .VTT FILE** (system document picker, SSA/ASS also accepted), caption size (A / A· / A+) and backdrop (none / dim / black) chips and, when subtitle addons answer, **LOAD N ONLINE SUBTITLES**. Captions start **off** for every title, whatever the profile: the player disables the text track type (`setTrackTypeDisabled(TRACK_TYPE_TEXT, true)`), so Media3 no longer auto-selects the first embedded track and burns it over the opening frame, and the dock reads `Subtitles · Off` until a track is chosen. A profile's subtitle language is still honoured as `setPreferredTextLanguage` (with `setSelectUndeterminedTextLanguage(false)`), so the first manual switch lands on that language instead of the first track in the file. Enabling online subtitles reloads the stream at the current position with the tracks attached, marks the first English track as default so it starts immediately, and the panel scrolls when a title returns dozens of tracks.
- **Tools panel:** equalizer presets + night mode, brightness/contrast/saturation, audio boost up to 200 %, subtitle scale/background and touch-lock toggles.
- **Hardware media keys:** `MEDIA_PLAY_PAUSE` / `HEADSETHOOK` toggle, `MEDIA_PLAY` / `MEDIA_PAUSE` set the state, `MEDIA_NEXT` / `MEDIA_FAST_FORWARD` skip +10 s and `MEDIA_PREVIOUS` / `MEDIA_REWIND` skip −10 s.
- **Volume keys:** `VOLUME_UP` / `VOLUME_DOWN` are intercepted in `CinemaActivity` (the shared base of `MainActivity` and `PlayerActivity`), which routes them through `VolumeKeys.handle` → `AudioManager.adjustStreamVolume(STREAM_MUSIC, …, AudioManager.FLAG_SHOW_UI)`. `FLAG_SHOW_UI` makes the platform render its own volume slider with the new level on every press, and both the key down and up are consumed, so neither the player OSD nor `PlayerView` ever sees them (`useController = false`, and no path forwards keys to `player.handleKeyEvent`). The 0–200 % boost slider in **Tools** is unchanged and still reached through the OSD.
- **Decoder modes:** AUTO (default) → HW → HW+ → SW cycle from the dock (the button shows the active mode as text), matching the Settings decoder type; cycling rebuilds the player and resumes near the current position. Tracks no platform codec accepts fall through to the bundled FFmpeg audio renderer.
- **Audio:** `Equalizer` + `LoudnessEnhancer` bound to the player audio session; night mode halves gain and applies a dialogue-friendly curve.
- **Volume normalization:** Settings → Playback → **Normalize volume** (default on, also togglable from the Tools panel as a `Normalize volume` chip) evens out loud effects and quiet dialogue with the transfer curve of FFmpeg's `acompressor`: RMS level detection across all channels with average channel linking, a soft knee, **−18 dB** threshold, **4:1** ratio, 10 ms attack, 250 ms release and **+6 dB** makeup gain, smoothed in the linear gain domain. The bundled Jellyfin FFmpeg extension ships only the decoder (`libffmpegJNI.so`, no libavfilter), so the same DSP runs in-process: the sink chain is `ToFloatPcmAudioProcessor` → `NormalizerAudioProcessor` → `ToInt16PcmAudioProcessor`, and about-to-be-encoded audio is decoded first, so both processors need PCM and encoded passthrough (AC3/EAC3/DTS/TrueHD) is withdrawn while normalization is on. With the toggle off the stock sink is restored, encoded passthrough included. The setting persists in `AppSettings.normalizeVolume` and is exported with the settings backup.
- **Open with:** closes the current player context and opens the system chooser directly, so any video player installed on the device can pick up the stream with its headers.

### Fullscreen and exit
- `Theme.StreamLineCinema` (NoActionBar, fullscreen, cutout-friendly) is applied directly in `AndroidManifest.xml` for both activities; the player keeps the screen on with `FLAG_KEEP_SCREEN_ON` and immersive system bars hidden.
- Back navigation unwinds detail → hidden route (Playroom opened from the top-bar SEARCH or the Import terminal, and Import itself, return to the tab that opened them) → tab → Home, then requires a **second BACK press within 2 s** ("Press back again to exit") before finishing the app.

## Notes & troubleshooting

- **APK size** comes mostly from Compose + Media3 and the bundled FFmpeg extension (about 6 MB of `armeabi-v7a` natives: `libavcodec`, `libavutil`, `libswresample`, `libmedia3ext`). A separate all-ABI test build (arm64-v8a / x86 / x86_64) is produced from a scratch tree for emulator runs.
- **HTTP streams** are allowed (`usesCleartextTraffic=true`); prefer `https://` URLs.
- **MDBList challenges:** the server reports a readable error; the app's direct fallback scrapes locally from the device, which may also be challenged. Use TMDB presets or a JSON manifest in that case.
- **No playable source:** the player only shows **No playable streams · Searched N sources** after the catalog and every enabled addon answered (each row keeps its own result). Import a catalog with direct links, register an addon in Settings for a source that answers, or check the per-addon error in the picker's SEARCH RESULTS list.
- **No online subtitles:** the SUBTITLES panel only offers the online button when a registered addon answers `/subtitles`. Titles imported before the IMDb id was stored carry no `tt…` id, so addons that only accept `idPrefixes: ["tt"]` (OpenSubtitles) stay silent until the title is re-imported or enriched from TMDB.
- **Live tab empty:** live addons must be registered in Settings and ACTIVE; press REFRESH after adding one. Cards marked as promos by the addon are intentionally hidden. `{catalog}: this selection returned no channels.` means the chosen selection-group value is empty upstream — pick **All** or **Clear all**; a channel that fails instead names the upstream reason (403/404/451, `empty playlist`, or external-only).
- **IPTV:** an M3U pasted into the EPG field is rejected (*This is an XMLTV guide, not a playlist*), and vice versa. A guide that fails or exceeds the 120 s download timeout only adds a line under the Live header; channels still list and play. `udp://`, `rtp://`, `rtsp://` and `rtmp://` channels always open in an installed external player, so a bare emulator shows Android's "No apps can perform this action" chooser. Parser coverage lives in `app/src/test/java/com/streamline/cinema/data/IptvParserTest.kt` (14 tests: M3U headers/attributes/EXTGRP/VLC options/pipes, relative URLs, XSPF, XMLTV incl. gzip and date offsets/colon/`Z`/ISO forms, zoneless device-timezone resolution, guide time-shift correction, automatic ZA `+0700` detection with sane/fixed/mixed guides left alone, legacy source migration and source JSON round-trip). Redirect-chain coverage lives in `HttpRedirectTest.kt` (8 tests: relative and absolute hops, header retention, credential stripping across origins, loop detection, hop cap, no-redirect and 304 responses).
- **Kids profile looks empty:** that is the whitelist working. Approve titles and channels in **Settings → Parental → MANAGE KIDS LIBRARY** (Settings itself is PIN-gated while Kids Mode is on). Before a custom PIN is set the PIN is **1234**; leaving the Kids profile and opening Search, Import or Settings all ask for it.
- **Imported list gone:** deleting a source with *DELETE LIST ONLY* keeps its titles in the library; *DELETE LIST + TITLES* removes the titles, their favorites and their watch progress.
- **External players:** install any video player (Just Player, VLC, MPV, MX Player, …) on the TV box; Settings lists detected packages for reference. **OPEN WITH** (⋮ menu, or the stall/failure panel) opens a queued picker: the system chooser is the default row, followed by every detected player with its package id, a read-only raw stream URL with **COPY**, and **DONE (BACK TO PLAYER)** to switch back before anything leaves the app. The app player pauses rather than tears down when the picker opens, so no second instance ever starts. A named player hand-off keeps the app player alive until that app actually covers the screen (`ON_STOP`), then closes it — after the transfer, only the external player is running. Returning to the app after a hand-off, or pressing **DONE** beforehand, resumes the same paused instance at the same position; hand-offs carry the stream URL with `FLAG_ACTIVITY_NEW_TASK` plus a `headers` String[] extra (`User-Agent` and any addon proxy headers, alternating key/value). If nothing accepts HLS or a video MIME, the picker reports that no external video player could open the stream.
- **DNS:** the resolver is app-scoped — other apps and the system keep using the box's own DNS. Some providers bind streams to the IP resolved by the *system* resolver, in which case switching presets can cause 403s; use System + a UA preset instead.
- **Composition-scoped coroutines:** only `LaunchedEffect` work (screen data loads, focus requests, addon collection, OSD timers) runs in composition scopes, and all of it treats cancellation as a normal exit instead of an error. Playroom search, quick imports and progress persistence run in ViewModel or app scopes, so tab switches, closing the preview or handing off to an external player cannot cancel or half-apply them.
- **Memory & resource guards:** the library JSON loads off the main thread behind the store lock (startup cannot ANR on a multi-megabyte catalog); URL/JSON imports, quick imports and scheduled syncs fetch, parse and merge catalogs on the IO dispatcher; EPG provider offsets are applied lazily instead of deep-copying the whole guide, and channel-name cleanup regexes are compiled once; the favourite season-sniff cache holds at most 64 series; and the HLS loopback proxy reads upstream with a 20 s idle timeout so one stalled CDN segment cannot pin a worker and wedge all six.
